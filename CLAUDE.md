# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Client (React/Vite) — run from `client/`
```bash
npm run dev       # Dev server with HMR at http://localhost:5173 (proxies /api/* → localhost:3001)
npm run build     # TypeScript check + Vite production build → client/dist
npm run lint      # ESLint
npm run preview   # Preview production build
```

### Server (Express/Node) — run from `server/`
```bash
npm run dev       # nodemon + ts-node, watches src/index.ts
npm run build     # tsc → server/dist
npm run start     # Run compiled dist/index.js

# What the guide generator WOULD read, without writing a guide or calling a model:
npm run research -- "The Legend of Zelda: Majora's Mask"
npm run research -- "Hollow Knight" "Bosses" "Charms"    # …for named chapters
```

`npm run research` exists because every failure that made the guides unusable was
a *research* failure — a franchise wiki answering for the wrong game, an
encyclopedia article where a walkthrough was wanted — and the only way to see
that layer used to be to generate the whole document and read it, a dozen model
calls and several minutes later. It prints the wiki it resolved (and whether that
wiki is shared across a franchise), the chapter list it would build on, and for
each section the pages it would write from, flagged ✓/✗ by the containment check.

### Docker (from repo root)
```bash
docker-compose up                          # Start app + Caddy + Watchtower
docker-compose --profile local-voice up    # …plus Kokoro + RVC on this box
docker-compose build                       # Multi-platform build (amd64 + arm64)
```

The Kokoro/RVC voice pipeline and ComfyUI image generation are location-independent
(the app reaches them via `KOKORO_URL`/`RVC_URL`/`COMFYUI_URL`). To offload it to a faster machine (typically the Ollama
box), run `docker-compose.voice.yml` there (`--profile gpu` for CUDA via
`docker/rvc/Dockerfile.gpu`, `--profile cpu` otherwise) and point the URLs at it
in `.env`; then start the dashboard box *without* `--profile local-voice`.
ComfyUI rides along in that same file's `gpu` profile and is GPU-only — there is
no CPU twin, because SDXL on the dashboard box is minutes per image, which isn't
a slower fallback but a hang. With `COMFYUI_URL` unset the drawing tools simply
aren't offered.

## Environment Setup

Copy `.env.example` to `server/.env` and fill in:
- `OPENWEATHER_API_KEY` — required for all weather/AQI/tile routes
- `CALENDAR_ICAL_URL` — optional Google Calendar iCal feed
- `DEFAULT_LAT` / `DEFAULT_LON` — recommended (falls back to GeoIP)
- `ELEVENLABS_API_KEY` — optional; falls back to `espeak-ng` on Pi
- `OLLAMA_URL` / `OLLAMA_MODEL` — LLM backend for `/api/chat`
- `YOUTUBE_API_KEY` — optional; makes `play_video` search reliable (falls back to scraping)
- `MEDIA_PLEX_URL` / `MEDIA_PLEX_TOKEN` — optional; turns on the Plex corner and the media voice tools. `MEDIA_SONARR_*`, `MEDIA_RADARR_*`, `MEDIA_BAZARR_*`, `MEDIA_SEERR_*`, `MEDIA_QBIT_*` each unlock one more feature (see `.env.example`); `scripts/collect-media-env.py`, run on the media box, fills them in from each service's own config
- `OLLAMA_IMAGE_MODEL` — optional; the model that rewrites image prompts (defaults to `OLLAMA_MODEL`). `OLLAMA_IMAGE_TIMEOUT_MS` caps it (45s). `OLLAMA_VISION_MODEL` — optional; the model that *looks at* a picture before a redraw (must have vision; defaults to the image model, then `OLLAMA_MODEL`)
- `HOST_UPDATE_SSH` — optional; `user@host[:port]` the container can SSH to for Settings → **Server** (apt, fwupd, Tailscale, container and self updates, reboot). Set up the host side with `scripts/host/install.sh` first
- `PORT` — defaults to 3001

## Architecture

### Layout
A full-screen kiosk SPA (720×1280 portrait on Raspberry Pi 5 / 7" touchscreen) with a center 3D particle sphere and four corner widgets. Designed for touch-only interaction at arm's length (minimum 14px, prefer 16–18px fonts).

```
┌──────────────────────────┐
│  [Plex]       [Time]     │   ← top-left amber (library/downloads/requests) / top-right yellow (clock+calendar+weather)
│         [Sphere]         │   ← center: Three.js particle sphere
│  [Draw]   [Tasks/Media]  │   ← bottom-left pink / bottom-right green|red
│         [StatusBar]      │   ← mode selector (work/rest/locked)
└──────────────────────────┘
```

- **[hooks/useWakeWord.ts](client/src/hooks/useWakeWord.ts)** — offline wake-word via Vosk running in a Web Worker; the wake phrases come from the selected assistant profile
- **[config/assistant.ts](client/src/config/assistant.ts)** — client half of the **selectable assistant** system: the profile table (name, `wakePatterns`, `wakePhrase`, tagline) + a reactive store (`useAssistant`, `setAssistantId`). Four profiles: **Martin** (default), **Jarvis**, **TouchSphere**, **Merlin**. The user picks one in Settings; the id is persisted via `POST /api/state/assistant` so the server's persona + voice follow. The server half (personality + TTS voice) is [server/src/config/assistant.ts](server/src/config/assistant.ts) — keep ids/names in sync. **This is the AI's identity** — the product/app is still "TouchSphere".
- **[components/BrowserOverlay.tsx](client/src/components/BrowserOverlay.tsx)** — full-screen browser window the assistant opens via `open_website` / `play_video` (see [server/src/routes/browse.ts](server/src/routes/browse.ts)). Three bodies: the YouTube embed, a live iframe, or reader mode for the majority of sites that refuse to be framed — with a manual reader ⇄ site toggle, since an iframe can still come back blank. Target lives in [hooks/useBrowse.ts](client/src/hooks/useBrowse.ts) and is opened by `useVoice` at the moment the spoken reply is revealed, so window and voice land together. A video is held (poster, then iframe-API pause/resume) for as long as the assistant has the floor — playback and the voice loop must never share the room
- **[components/widgets/MediaListWidget/GuideView.tsx](client/src/components/widgets/MediaListWidget/GuideView.tsx)** — the **game guide**, full screen, in two layers: a chapter list (nothing but the chapters, each with its kind chip, `x/y` and bar) and, on tapping one, that chapter's own scrolling page of tickable steps with its walkthrough video and prev/next. Steps deliberately never appear in the list — a 12-chapter game is a few hundred of them. A chapter row is **two tap targets**: the body opens it, the trailing circle ticks the whole chapter off where it stands, because picking up a guide for a game you're part-way through means marking several chapters done before reading anything. Inside a chapter, "Mark all done" and "Redo this chapter" sit at the top, above the steps, since both exist precisely to avoid scrolling the steps. The steps themselves are grouped into **collapsible sub-chapters**, and a *finished* part collapses to a single line by default — so a chapter you're half-way through opens on the part you're actually on rather than thirty struck-through steps. Tapping a heading overrides that for good, so the list stops rearranging itself once the user has an opinion. Both layers carry the **same round X at top-right as every expanded widget** — that's the one gesture in this app that already means "done with this screen", and a chapter also keeps a labelled "← Chapters" pill so back-one-level and leave-entirely are never the same guess. The guide previously offered only a small top-*left* arrow, which took two taps to get out of a chapter and sat where nothing else in the app puts its exit Data comes from [hooks/useGuides.ts](client/src/hooks/useGuides.ts): `useGuides()` for the per-game summaries that draw the row/pill bars, `useGuide(itemId)` for the document itself. Both follow the server's `guide` SSE event, which is what makes a generation *fill in while you watch* and a spoken "tick that off" move the bar under your eyes. Note `/api/guides` sends `Cache-Control: no-store`: without it Chrome heuristically reuses the document and those live refetches silently return the old one. Videos are handed to the existing [BrowserOverlay](client/src/components/BrowserOverlay.tsx) via `openBrowse`
- **Overlay stacking** — five portals can be on screen at once, and their z-bands are load-bearing: **9400/9390** ImageOverlay window + backdrop → **9300/9290** PlexPlayer → **9200/9190** BrowserOverlay window + backdrop → **9100** GuideOverlay → **9000** `Widget`'s expanded overlay. A generated picture sits on top of everything because it is the thing that was just asked for and can be asked for while a video is playing. The Plex player sits above the browser window because a film asked for from the couch should cover whatever page was up, and `openBrowseFromPayload` closes it when a video, page or guide arrives, so there is only ever one window with sound. A video opened from inside a chapter must cover the guide, and the guide must cover the Watch/Play list it was opened from. The guide sat at 8900 until it was reported invisible — tapping a game in the *expanded* list rendered the guide under the very widget it was tapped from, so it only appeared once the list was closed. A widget's inner controls (close button at 9999, grab handle at 9500) are inside its own stacking context and can't escape above the guide, so they need no separate handling
- **[components/GuideOverlay.tsx](client/src/components/GuideOverlay.tsx)** + **[hooks/useGuideOverlay.ts](client/src/hooks/useGuideOverlay.ts)** — which guide is on screen. The guide is a top-level overlay rather than a layer inside the media widget because two unrelated things open it: a tap on a game, and the assistant being asked out loud (`show_game_guide`) — and a voice command can't reach into a component's `useState`. Same module-store shape as `useBrowse`, and `openBrowseFromPayload` routes the `guide` and `close` display kinds into it
- **[components/ImageOverlay.tsx](client/src/components/ImageOverlay.tsx)** + **[hooks/useImageOverlay.ts](client/src/hooks/useImageOverlay.ts)** — the full-screen **generated picture**. Same module-store shape and the same reason as the guide overlay: `generate_image` is a voice tool, and a voice command can't reach into a component's `useState`. The distinguishing feature is that **the frame goes up before the picture exists** — a render is ten to thirty seconds and the overlay opens at the moment the spoken reply is revealed, so the empty frame with its phase text *is* the feedback; the alternative is half a minute of silence after "drawing that for you now". `useImageJob()` follows one render to completion from **two** sources, and needs both: the `image` SSE event, plus a `GET /api/image/job/:id` on mount, because the display payload and the SSE frame race — on a re-show or a page reload every frame for that job is already in the past and the overlay would sit on "drawing" forever for a picture that finished before it opened. The progress bar is measured against **[server/src/image-timing.ts](server/src/image-timing.ts)** — a persisted history of finished renders keyed by style, effective steps, pixel count and whether the checkpoint was already in VRAM — not against the duration of whatever the box drew last, which is what it used to be and which is wrong for every render that isn't a repeat of the previous one (turbo is ~10 steps where NoobAI is 28; draft is 12 where high is 44; the megapixel knob spans 0.5 to 16). The estimator has four tiers and **names the one it used** on the wire (`etaBasis`), because "measured from 6 earlier renders of this style at these settings" and "a rough guess, nothing drawn with this style yet" deserve different amounts of trust and the screen can only pass that on if it is told. Warm and cold are separate populations rather than one scaled by ratio: 20–40s of checkpoint load is most of a short render and a rounding error on a long one. Still capped below full, and absent entirely with no history: a bar parked at 100% while nothing happens is worse than no bar. Alongside the bar, the frame shows the job's **`detail`** — the server's full-sentence account of what is happening (which style, how many steps, at what size, what the wait is being spent on, how long it should take) — as a second field beside the short `phase`, because the two are read in different places: `phase` goes in the queue strip's hundred-pixel rows and the collapsed corner, `detail` fills a frame that is otherwise an empty rectangle for half a minute. `refreshQueue()` on the server re-announces every waiting job whenever one leaves the line, since a status that says "3rd in the queue, about 2m before this one starts" goes stale the moment anything ahead of it moves — and that job is precisely the one that gets no frame of its own. `openBrowseFromPayload` routes the `image` kind into it, **above** its own `^https?://` guard — a picture that is still being drawn has no url at all, and a finished one carries a relative `/api/image/file/…` path that the guard would drop. Once the picture exists the frame also carries the two things anyone does with one, both of them here rather than in the gallery grid because looking at a render full size is the moment you decide it's nearly right: **‹ / › arrows** over the image, and **"Use as prompt"**. The arrows read the gallery from a `GET /api/image` the overlay makes itself — it is opened from three places (a thumbnail, a queue row, a spoken `generate_image`) and only one of those has the list to hand — refetched when a render reports `ready`, since the picture being watched joins the list at the moment it lands; a stored image keeps the id of the job that drew it, so one id addresses both halves. They are **absent, not disabled**, at either end, because a dead arrow on a touchscreen is a tap that looks broken. **Tapping the picture itself fills the screen** — no caption, no buttons, no frame, just the image edge to edge with the close button and the arrows — and tapping it again brings the frame back; paging with the arrows while filled stays filled (the state is stamped with the next open's `seq` ahead of time), a fresh open starts framed. **"Change this"** is the img2img half — it carries the picture itself, not just its words, and is offered only for one that is actually in the gallery, since that is the same condition that gives it an id the GPU box can be handed. "Use as prompt" is deliberately a separate button rather than a mode of it: "another go at this idea" and "this exact picture but at night" want different starting points, and guessing wrong costs a minute of GPU either way. Both write into **[useImagePrompt.ts](client/src/hooks/useImagePrompt.ts)**, which is where the Draw panel's compose field and its source picture now live: the overlay is a portal at the top of the tree and cannot reach into `ImageExpanded`'s `useState`, the same problem `useBrowse` and `useGuideOverlay` solve the same way. The source lives in that same store rather than a second one because it is a piece of the composed request exactly as the prompt is — the panel draws a card for it, the Draw button becomes "Redraw it", the orientation row hides itself, and all three would otherwise have to be kept in step across two stores. "Use as prompt" clears the source explicitly, since inheriting one from an earlier tap on the other button would silently turn one into the other. Both raise an `onDrawPanelRequest` event App.tsx subscribes to, because filling a field nobody can see is not reuse — the corner has to come up on it. Side effect worth having: the draft now survives closing the panel. The prompt caption itself carries `.selectable-text`, which opts it out of the app-wide "a tap is never a text selection" rule and puts `-webkit-touch-callout` back, so a long press on a phone can lift one phrase out of it; the buttons cover the whole string, which is the only thing the kiosk can manage
- **[components/widgets/ImageWidget/](client/src/components/widgets/ImageWidget/)** + **[hooks/useImages.ts](client/src/hooks/useImages.ts)** — the bottom-left **Draw** corner: the tap half of `generate_image`. The Draw button is **not gated on the GPU being busy** — it reads "Add to the queue" instead, and the **queue strip** below it lists what is waiting in draw order: the live one with the server's own phase text, the rest numbered, each with an × that drops it (the guide's two-tap-targets-per-row split — the body opens the full-screen frame to watch it, the × removes it). It is absent entirely when the GPU is idle, since an empty list headed "Queue" is a permanent reminder of a feature nobody is using. The collapsed pill reads "Drawing… +3 queued", because "still going" and "still going, three to come" are different answers to the only question someone walking past has. Same job engine, same store, same full-screen viewer, so a picture is identical however it was asked for, and the corner pill reads "Drawing…" for a render the *assistant* started. The gallery is **always N across, never a breakpoint** — three by default on every screen, changed with the per-row slider (1–12) above it or by pinching the grid, and kept per device in `localStorage` ([useGalleryColumns.ts](client/src/hooks/useGalleryColumns.ts)) because the same build runs on the 7" kiosk, a phone and a desktop and the right number differs on each. A **Recent** row of the last six distinct prompts sits above the starters whenever the field is empty, since re-typing forty words on the on-screen keyboard is the most expensive thing this app asks of anyone, and a **camera button** (`<input capture="environment">`) beside "Use my own picture" opens a phone's camera straight into "Change this". The Style row lists the checkpoints ComfyUI reports and is hidden when there is only one — one installed model is not a decision. It's a horizontal scroller rather than a `<select>` because a native dropdown opens an OS popup TouchKio renders badly. `enabled` is **re-polled every 30s while it is false**, and only while false: it used to be fetched once at mount, which latched the panel on "isn't reachable" through both of the races that actually happen on this hardware — the Pi booting before the server, and the GPU box being switched on hours later — on a device with no keyboard to reload it with. **[AdvancedPanel.tsx](client/src/components/widgets/ImageWidget/AdvancedPanel.tsx)** is the tuning half — the knobs in [image-params.ts](server/src/image-params.ts), collapsed by default because Style and Quality cover almost every session and a kiosk panel that opens on nine controls is one nobody reads. Its closed header lists whatever is actually overridden, since the failure mode of a collapsed panel is forgetting what you left inside it (and the Quality row dims itself and says "overridden" when Steps is set, so a preset that isn't in effect can't look like it is). Numbers are **−/+ steppers around a typed field, never sliders** — a fingertip can't land 0.05 on a 7" screen. The steppers are for nudging; the middle of every row is a real input that opens the **number pad** ([TouchKeyboard](client/src/components/TouchKeyboard.tsx) with `numeric`, a dialler layout rather than the letter board), because eight taps of + is not a way to ask for 96 steps and every knob here has a value somebody eventually knows exactly. Each row keeps its one-tap "Auto" to get back out — and clearing the field does the same thing, since the Auto text is the placeholder — and stepping *up* out of Auto lands on the control's minimum rather than on one step (cfg 0.5 is a value no model wants). The chip rows (megapixels, align-to) are **shortcuts, not the range**: `LIMITS` in useImages.ts mirrors the server's bounds so a typed value is clamped identically on both sides, and each label states its range, because a field that accepts 400 steps and then shows 150 without saying so reads as the panel losing the setting. Since the knobs are per style, the loader effect carries a cancelled guard that is load-bearing rather than hygiene: tapping through three styles fires three requests, and the slowest one winning would leave the panel describing a style you aren't on — which the next tap would then save *against* the one you are
- **[hooks/useServerEvents.ts](client/src/hooks/useServerEvents.ts)** — one shared `EventSource` on `/api/system/events` with `subscribe(event, cb)`. The restart signal, guide progress (`guide`) and the guide activity feed (`guide-activity`) all ride it; a per-hook EventSource would cost the Pi a held-open request and a heartbeat per widget
- **[hooks/useGuideActivity.ts](client/src/hooks/useGuideActivity.ts)** + the **Guides** tab in [SettingsPanel.tsx](client/src/components/SettingsPanel.tsx) — what the guide researcher is doing, in three blocks: what's generating right now (phase + bar), every guide on disk with its status, and the activity feed itself (tap a guide to filter the feed to it). One GET for the backlog plus the SSE event for everything after, merged on the server's monotonic entry id so a frame arriving mid-fetch can't land twice
- **[components/TouchKeyboard.tsx](client/src/components/TouchKeyboard.tsx)** + **[components/TouchInput.tsx](client/src/components/TouchInput.tsx)** + **[components/touchTextEdit.ts](client/src/components/touchTextEdit.ts)** + **[components/keyboardLayouts.ts](client/src/components/keyboardLayouts.ts)** — the on-screen keyboard. The kiosk has no physical one and the native IME is suppressed everywhere (`readOnly` + `inputMode='none'`), so this is the **only** way text is typed on the device. It used to be append-only — every key did `value + char`, ⌫ did `slice(0, -1)` — which made the caret a fiction: no fixing a typo mid-sentence, and clearing a long prompt meant forty taps. Every edit now happens at the target element's **real selection**, passed in as `targetRef`, and that one change turns on three things at once: tap to put the caret anywhere and type there, drag / double-tap / long-press to select a run, and type or ⌫ over a selection to replace or bulk-delete it. **Selecting was already native behaviour on a `readOnly` input — it was simply never being read.** Two pieces of machinery make it hold: a `useLayoutEffect` that restores the caret after every controlled re-render (React rewrites the whole value and the browser's answer is to drop the caret at the end, which would defeat the file on every keystroke), and a document-level `selectionchange` listener, the only event that covers caret moves inside a form control from tap, drag and our own edits alike. `targetRef` is optional and its absence degrades to the old append-only behaviour — honest rather than tidy, since a caret nobody can see or move is worse than none. There is deliberately **no toolbar of caret buttons**. There was one — undo, four arrows, select-all, copy, paste — and it was the wrong answer to "let me move around the text": arrow keys on a touchscreen are worse than the thing they replaced, and the row sat between the field and the letters. Putting the caret somewhere is a **tap in the field**, which is why `TouchInput` is **not `readOnly`** — it was, to keep the native IME away, but Chromium paints no caret at all in a readonly field, so tapping into the middle of a prompt moved an invisible caret and read as the tap doing nothing. `inputMode='none'` carries that job alone; the trade is that a physical keyboard can type straight in, which is why the field keeps a real `onChange` (and is a feature on a desktop browser). On top of that: hold-⌫ to repeat, double-tap ⇧ for caps lock, and a **`numeric` dialler pad** for number fields — its own return rather than another row variant, because nothing about the letter board applies (no ⇧, no 123/ABC, no space) while caret, selection, undo and ⌫-repeat are all the shared code. Clipboard tries `navigator.clipboard` and falls back to a module-level string, because a kiosk has nobody to answer a permission prompt. The pure text rules live in [touchTextEdit.ts](client/src/components/touchTextEdit.ts) — `insertAt` / `deleteBack` / `caretTarget` / `ordered` — split out of the component so caret arithmetic can be reasoned about and exercised without a DOM, which matters more here than usual: on a device with no physical keyboard, a caret bug is not something the user can type their way out of. `deleteBack` steps back two code units over a surrogate pair so ⌫ can't leave half an emoji, and returns null (not a no-op edit) at position 0 so held-⌫ doesn't fill the undo stack. **The key layouts follow iOS**, in two shapes picked by viewport width: the **iPhone** board (ten columns, ⇧ and ⌫ flanking `zxcvbnm`, `asdfghjkl` inset half a key each side) below `TABLET_MIN_WIDTH`, and the **iPad** board (⌫ on the end of row 1, `return` on row 2, `,` and `.` joining the bottom letter row, ⇧ at *both* ends, taller keys) at 768px and up. The point is muscle memory, not looking Apple-ish — these are the positions a thumb already expects, so the `123` / `#+=` pages carry iOS's own character sets, and the iPad board reuses the iPhone's sets rather than Apple's slightly different iPad ones, because punctuation that moves between two devices the same person uses is worse than punctuation one row off Apple. **Width, not user-agent**: it is the thing that actually decides whether eleven keys fit, it follows an iPad rotating with nothing to listen for, and it puts the 720px-wide Pi on the phone board without a special case. Layouts are data (`KeyDef[][]`, a `w` flex weight per key) rendered by one `renderKey`, and **every row of a board sums to the same weight** — 10 on the phone, `ROW_UNITS` (12) on the tablet — so a letter key is the same width on all three rows; `unevenRows()` exists to assert that rather than eyeball it, and it caught exactly that bug on the tablet board. The one deliberate exception is iOS's own: the phone's punctuation row is five wide keys, not ten, so those carry an explicit 1.25 weight to still total 10. The phone's bottom row makes **two deliberate departures from iOS**, both fixes rather than decoration: `,` and `.` **flank the space bar** (on an iPhone the comma is two taps away on the `123` page — fine for a text message, bad where the longest thing anyone types is a comma-separated image prompt; the tablet board doesn't need it, `,` and `.` are already on its letter row), and **nothing that commits sits next to space** — iOS's single `return` has to be two keys here (`↵` types a newline, `Done` closes), and the first version put `↵` immediately right of the space bar where it was hit by accident constantly. Both now sit past `.` at the far end, so the keys either side of space are punctuation and a mis-tap costs a character, not the field. TouchInput additionally scrolls its field into view on open — the keyboard covers the bottom third of the screen and half this app's fields live down there
- **[components/widgets/PlexWidget/](client/src/components/widgets/PlexWidget/)** + **[hooks/usePlex.ts](client/src/hooks/usePlex.ts)** + **[components/PlexPlayer.tsx](client/src/components/PlexPlayer.tsx)** — the top-left **Plex** corner, which took the slot the weather had (the weather is now the third tab of the Time corner and a one-line temperature-and-sky under the date on its pill; [WeatherMap](client/src/components/widgets/WeatherWidget/WeatherMap.tsx) grew a `nested` prop that gives it an explicit viewport height, since inside the Time corner Widget's wrapper is a natural-height scroll container and `h-full` resolves to nothing). The pill answers the walking-past question — "Continue · <show> S2E4", or the download count — and the panel is three tabs, each behind a different service and **absent, not empty, when that service isn't configured**: **Library** (search, continue watching, recently added, and an item page per film/show/season/episode with the **languages** block — every audio and subtitle language across the files with `n/total` counts, the thing Plex's own apps only answer by starting the file and opening a menu — plus audio/subtitle pickers for a playable item, Bazarr's "still looking for" line, and the seasons/episodes with a per-episode language line and their own ▶); **Downloads** (see [downloads.ts](server/src/downloads.ts)); **Requests** (Seerr search with the status badge — requested / downloading / in the library — and the recent requests). **Play here** hands the item to `PlexPlayer`, a full-screen HLS player (hls.js, lazy-loaded; native HLS on Safari) that pauses while the assistant has the floor exactly as BrowserOverlay does, reports progress to Plex every 10s so the position survives to the TV app, and seeks by **starting a new transcode session at the offset** — the transcoder emits a playlist whose clock starts at the offset, so a scrub is a new session rather than a seek. **Play on…** lists the other Plex apps on the network and sends the item there. All three module stores (`openPlexPlayer`, `requestPlexPanel`, `usePlexStatus`) exist for the same reason `useBrowse` does: `play_media` and `whats_on_plex` are voice tools, and a voice command can't reach into a component's `useState`
- **[components/Companion.tsx](client/src/components/Companion.tsx)** + **[hooks/useClientRole.ts](client/src/hooks/useClientRole.ts)** — the **phone layout**. Below the `sm` breakpoint (or with `?mode=companion`, which the home-screen manifest's `start_url` sets) the app is a *remote for the kiosk* rather than a cramped copy of it: a home screen with what the kiosk is playing (pause/resume/stop), what's up next ("on the kiosk" / "here"), and a tab bar that opens the same full-screen panels the corners open, plus Settings. - **[guides.ts](server/src/guides.ts)** + **[guide-generator.ts](server/src/guide-generator.ts)** + **[routes/guides.ts](server/src/routes/guides.ts)** — **game guides**: one researched, tickable walkthrough per game, organized the way that game's own community organizes it. The store is `guides.json` in `$CACHE_DIR`, keyed by `MediaItem.id` and deliberately *not* folded into `media.json` — that file has two non-atomic writers and a field-whitelisting normalizer that has already destroyed a column once. Every array in a guide is model-generated, so the store caps and re-validates on both read and write, quarantines a corrupt file instead of overwriting it, and writes atomically (the `memory.ts` pattern). Generation is a background job: `startGuide()` writes a `generating` skeleton and returns, so the assistant can answer in one breath while the work outlives the conversation. It is **overview first, then detail, at every level** — for one reason: a local model asked for a long answer doesn't answer badly, it stops partway, and half a JSON object parses as nothing, so no call is ever asked for much at once. Stage 1 is one call for the section list (dungeons/chapters, then collectibles and side quests) plus which sections count toward 100%. Stage 2a is one call per section for its steps **as bare one-line strings, no explanations**, already divided into the chapter's own **sub-chapters** ("Getting there", "Boss: Odolwa") — saved and broadcast at once, so the chapter is a working tickable checklist from that moment. A sub-chapter is a `group` label on `GuideStep`, not a nested array: consecutive steps sharing a group *are* that sub-chapter, and the chapter page derives its headings, per-part counts and collapse state from those runs. The steps stay one flat ordered list because the 1..n numbering the detail pass keys notes to, both progress bars, tick-one-step, tick-a-chapter and `carryTicks` all walk `section.steps` — nesting would fork every one of them into a two-shape traversal for something the UI can group on its own. A guide written before sub-chapters existed, or by a model that ignores them, is one untitled run and renders as the plain list it always was. Stage 2b walks those steps in batches of `DETAIL_BATCH` (8), one call per batch, asking only for the note on each, patched into the stored guide **by step id** (the chapter has been on screen and tickable since 2a — rewriting the array would un-tick what the player ticked meanwhile). Replies are keyed by the step number sent in the batch and numbers outside it are dropped wholesale, because a model that renumbers from 1 would otherwise smear one batch's notes across another's steps. The guide is saved and SSE-broadcast throughout, so a late failure costs the explanations, not the chapter. This replaced a single per-section call asking for 30 steps *with* notes from 26k chars of research, which routinely ran past the timeout or truncated — landing as an empty chapter. Research happens here rather than through the chat tool loop because that loop truncates tool results at 8k chars and caps at 5 rounds. A section that fails is marked failed and the rest continue; a restart mid-job is swept by `sweepInterrupted()` at boot rather than leaving a permanent spinner — to `ready` with the unfinished chapters flagged when anything survived, `failed` only when nothing did, because failing a whole document over two bad chapters points the user at a full rebuild that costs them every ticked box. **`OLLAMA_GUIDE_NUM_CTX` (default 16384) is load-bearing**: Ollama defaults `num_ctx` to 4096 and discards the overflow from the *front* of the prompt, which is where the research notes are — left at the default the model writes each section from instructions with the evidence sheared off, which reads as "the guide has no detail". **`OLLAMA_GUIDE_MODEL`** (default: `OLLAMA_MODEL`) picks the model that writes guides, which need not be the one holding the conversation: the chat model is chosen for latency because someone is waiting at the kiosk, and nobody is waiting on this — a guide is a dozen background calls over minutes, and synthesizing 26k characters of research into a route is a harder job than answering "what's the weather". **Three quality gates run before anything is stored**, each for something that shipped: `dropPlaceholderRuns()` deletes runs of steps differing only by a digit ("Obtain Heart Container 1 from boss" ×8, "Collect 4 Pieces of Heart for Heart Container N" ×13) — a model with notes that never list the things enumerates the *count* instead of the *contents*, which renders as a tidy checklist that says nothing and moves the 100% bar; the whole run goes rather than all-but-one, since emptying the chapter is what makes the repair pass re-research it. `isVacuousNote()` drops a note that only restates its step ("Travel to Woodfall" → "Travel to the cardinal direction of Woodfall"), which is strictly worse than the honest plain checkbox it falls back to. `statedTotal()` reads "there are 24 masks" out of the research, tells the model the target up front, and flags a list that came back under two-thirds of it — a collectible list that stops short is the one failure that actively lies, because the player ticks every box and the bar reads 100% on an unfinished game. The repair pass therefore retries chapters that are empty **or short**, and keeps the longer of the two results — a wider search can come back with less, and the retry exists to improve the chapter, not gamble it (an explicitly user-requested rewrite deliberately skips that guard, since they want it replaced however it comes out). **A single section can be re-researched on its own** (`regenerateSection`, `POST /api/guides/:itemId/sections/:sectionId/regenerate`, tool `regenerate_guide_chapter`), leaving every other chapter and its ticks alone; `carryTicks` matches steps by normalized text so a rewrite keeps the boxes that survive it. Voice side: `create_game_guide` / `get_game_guide_progress` / `check_off_guide_step` in [dashboard-tools.ts](server/src/routes/dashboard-tools.ts), and the screen-driving half in [routes/guide-view-tools.ts](server/src/routes/guide-view-tools.ts) — `show_game_guide` (full screen, optionally straight to a chapter named or numbered), **`read_guide_step` / `next_guide_step`** (the voice-over: read the first unticked step of the current chapter with its note, then tick it and read the next on "next"/"done" — hands are on a controller, so a step at a time and never a chapter), `list_guide_chapters`, `play_guide_video`, `check_off_guide_chapter`, `regenerate_guide_chapter`, `delete_game_guide`, `close_screen`. Those return a `display` payload like the browse tools, so **everything reachable by tapping is reachable by asking**. `pushGuide` in [guide-events.ts](server/src/guide-events.ts) is the one place that broadcasts a change (generator, voice tools and the REST route all call it; it lives on its own to keep those three from importing each other)
- **[research.ts](server/src/research.ts)** — where guide content comes from. The wiki host is discovered by probing slug candidates against fandom.com/wiki.gg (`zelda`, `hollowknight`, `celestegame`…). Two per-farm quirks are handled: `prop=extracts` isn't installed on every Fandom wiki, so those fall back to rendered HTML through the same readability pass reader mode uses, and Wikimedia serves `api.php` under `/w/`. Three things here are load-bearing, and each fixed a way the guides came out unusable:
  - **Which game is this?** The worst thing this file can do is return pages about a *different* game, because the generator is told "write only from the notes" and obeys — a shipped Majora's Mask guide had an Age of Calamity final battle, a Spirit Tracks item list and Skyward Sword's side quests, all faithfully transcribed. The cause is **franchise wikis**: `majorasmask.fandom.com` 301s to `zelda.fandom.com`, which covers twenty games, so an unscoped search for a section called "Sidequests" exact-matches whichever game ranks first — and `wikiSearchBestFirst` then *promotes* it. `findGameWiki()` returns `{ host, shared }` and detects `shared` three ways, because all three occur: the probe redirected; the wiki's name covers only part of the title; or the game IS its franchise's namesake ("The Legend of Zelda"), which nothing in the name reveals and which is caught by the wiki having a `Category:Games` with several games in it. On a shared wiki every query is scoped by `gameQualifier()` ("Majora's Mask", not the full title) and every page must pass `mentionsGame()` — one string check that would have rejected every wrong-game chapter, since a Spirit Tracks page never says "Majora"
  - **`communityChapters()` is the chapter list, not `communityTableOfContents()`.** A wiki article's headings describe the *article* — Plot, Development, Reception — and outlining from them is how a nine-dungeon game shipped as three chapters recapping the cutscenes ("Arrival to a Doomed Land"). Those four names are literally the `Story` section's subheadings. So the TOC now drops encyclopedia headings *and their whole subtree* (the parent is filtered by name; the plot-act children can only be caught by ancestry) and is used **only as a fallback when the categories come up empty**. The real source is the wiki's **per-game categories**, which describe the *game* and are game-scoped by necessity on a shared wiki: `Category:Dungeons in Majora's Mask` is exactly the ten dungeons. They're found by searching the category namespace for the game's name rather than guessing names, because the conventions in the wild are both "Dungeons in Majora's Mask" and "Bosses (Hollow Knight)" — and searching the name alone also surfaces the lists no fixed guess would ask for, `Masks in Majora's Mask` being the one whose absence shipped a mask chapter with 5 of 24. A category naming a game explicitly must name *this* one, which is what keeps `Areas (Silksong)` out of a Hollow Knight guide even though that wiki isn't "shared"
  - **Source order is conditional, not fixed.** Wiki-first exists because scraped search answers a burst of queries with a CAPTCHA — real without a key, and still the default there. But with `OLLAMA_API_KEY` set that constraint is gone and wiki-first is actively wrong for a walkthrough: a wiki *describes* a dungeon where a walkthrough site *routes you through* it, and the old order only reached the open web when the wiki returned nothing, which it never does. Hosted search also returns the page's **full text inline** (tens of thousands of characters), which matters beyond the saved round trip: the walkthrough sites worth reading — StrategyWiki among them — answer this server's own fetch with a Cloudflare 403, so re-fetching would throw the good text away. Hence `webFirst`, set for progression sections when hosted search is live. Wikipedia remains the next fallback, then the open web

- **[image.ts](server/src/image.ts)** + **[routes/image.ts](server/src/routes/image.ts)** + **[routes/image-tools.ts](server/src/routes/image-tools.ts)** — **image generation** through ComfyUI. Location-independent exactly like the voice pipeline — the app only ever talks HTTP, so `COMFYUI_URL` decides where it runs, and in practice that's the GPU box (`docker-compose.voice.yml` starts ComfyUI under the same `gpu` profile as Kokoro and RVC). **The one structural difference from TTS is that there is no fallback**: the voice chain always has espeak underneath it, so a dead GPU box costs an assistant her voice, not her ability to speak — there is no espeak for pictures. So `IMAGE_TOOLS` is **empty unless `COMFYUI_URL` is set**, and the system prompt's DRAWING paragraph is omitted with it; a model that can see a `generate_image` tool will cheerfully promise a picture before discovering there's no GPU behind it. **The render deadline covers drawing, not queueing**, and that distinction is load-bearing: ComfyUI is a shared box whose queue can hold work from another client, from an earlier run of this server that was restarted mid-render, or simply from four pictures asked for in a row. Counting that wait against a render's own budget made a busy GPU fail *every* job it was given — and because a timed-out job used to be abandoned while its prompt stayed queued, each failure left an orphan behind that made the queue deeper, so the next render timed out sooner. Thirteen deep, nothing could be drawn at all and the queue had to be cleared by hand. So `awaitOutput()` polls `/queue` and pushes the deadline out for as long as the prompt is still pending (reporting "waiting for the GPU" while it does), a separate `COMFYUI_QUEUE_WAIT_MS` bounds the total so a wedged box is still given up on, and `dropFromQueue()` removes our prompt whenever we give up — the abandoned-work half is what turns a slow render back into just a slow render instead of a spiral. Generation is a background job for the same reason guides are — a cold ComfyUI pays 20–40s loading a checkpoint into VRAM before it draws a step, and the assistant can't hold the conversation open that long — so `startImage()` registers the job, returns, and reports over the existing `image` SSE event. Jobs are **drawn one at a time but may be queued** — `startImage()` appends to a serial promise chain, `pendingJobs()` reads it back in draw order, and `MAX_QUEUED` (8) caps it. One at a time because two SDXL renders on one card don't go twice as fast, they thrash VRAM; queued because asking for four pictures is one thought, and the alternative was standing at the kiosk for ninety seconds between them. A full queue is refused by **returning an already-`failed` job rather than throwing**, so the REST route and the chat tool get one shape back and neither grows an error path of its own (the route also 429s first, so the panel can print the reason under the button the finger is on). `cancelJob()` drops a **queued** job only — the promise link can't be unlinked, so it marks the job `cancelled` and `run()` returns on that mark; a render already on the GPU is seconds from existing and abandoning it would waste work that is already paid for, while what a mis-tap actually produces is the four behind it. Finished jobs are pruned past `MAX_TRACKED_JOBS` (40) — this Map lives in a process that runs for months and the queue makes entries arrive in bursts. `GET /api/image/queue` is the catch-up half (SSE only carries what happens from now on) and `POST /api/image/job/:id/cancel` the other end; the client keeps its own copy of the queue from `image` frames and re-orders it by the `queuedAt` on the wire, because a frame is pushed when **one** job changes and every other job's position moves when the one in front of it finishes. `/prompt` takes ComfyUI's **API-format** export (a flat map of node id → `{class_type, inputs}`), *not* what the ordinary Save button writes — feeding it the latter is the single most common way this fails and it fails with a bare 400, so `baseGraph()` detects the UI shape and says which export to use. The prompt, size and seed are patched in **by node class, not by node id**, so a workflow someone exported themselves keeps working (their KSampler is rarely node `3`); the two `CLIPTextEncode` boxes are the interesting case — nothing in either node says which is the negative one, so they're resolved by following the sampler's own `positive`/`negative` links, which is the only place that distinction exists. `conditioningText()` follows that link **through the conditioning chain** rather than stopping at the first hop, because a model family that carries guidance *in* the conditioning puts a node in between: FLUX's positive arrives via `FluxGuidance` and its negative via a `ConditioningZeroOut` of the positive, so the one-hop version failed every FLUX graph with "positive prompt does not reach a text node" and shut out every FLUX workflow anyone might drop on the volume. It is depth-limited because a workflow is user-supplied data and a cycle must not hang the render. The `negId !== posId` guard beside it is load-bearing, not defensive: a zeroed-out negative resolves to the *same* text node as the positive, and writing to it would replace the prompt with the negative and draw a picture of everything the user didn't ask for. A custom graph goes at `$CACHE_DIR/workflows/txt2img.json`, on the volume so it survives a rebuild. Finished PNGs are written atomically into `$CACHE_DIR/images` and served by `GET /api/image/file/:file` — the artwork.ts cover pattern, with one addition: **the store is capped and pruned oldest-first**, because unlike cover art (bounded by the length of the Watch/Play list) generated images grow without limit on a volume that lives on the Pi. `COMFYUI_URL` deliberately bypasses `isPublicHttpUrl()` — that guard exists for *model-supplied* URLs, and this is operator config pointing at a tailnet address, exactly as `RVC_URL` is. **Redrawing** (`source` + `denoise` on `POST /api/image/generate`, `redraw_image` by voice, "Change this" in the viewer) is plain **img2img** and works on every style, not just Anima: the source is encoded to a latent, the sampler starts from that instead of an empty one, and `denoise` says how much of it to throw away — ComfyUI's own Anima template ships the same thing behind a "Load Image" switch node, the same kind of switch the turbo LoRA was behind. Spliced by **rewiring** exactly like that LoRA: a `LoadImage` + `VAEEncode` pair replaces whatever fed the sampler's `latent_image`, and the **VAE is found by following the `VAEDecode`'s own `vae` link** rather than by hunting for a loader class — that link is the only place a graph says which VAE this pipeline uses, the same reasoning as resolving the two `CLIPTextEncode` boxes through the sampler's positive/negative links. The empty latent is left in place, unreferenced, so ComfyUI never executes it. The source has to physically reach the GPU box — there is no shared filesystem across the tailnet — so `run()` uploads the PNG through ComfyUI's `POST /upload/image` (multipart, named after the image id with `overwrite`, so redrawing one picture five times leaves one file rather than five) and the name that comes back goes into the node. The **size comes from the source and orientation is hidden**, because a VAEEncode latent is the source's own shape and leaving three buttons on screen that the render ignores is exactly the silent-override failure the per-style params exist to avoid. `source` is a **gallery id, never a path or a URL** — the operator-vs-model distinction again: the gallery is the only closed set of images this app will hand to the GPU. That invariant is also what decides the shape of **starting from a picture of your own** ("Use my own picture" in the Draw panel, `POST /api/image/upload`): rather than a second path into the GPU, an upload is simply one more entry *in the gallery* (`addUploadedImage()`, `origin: 'upload'`), so redraw, "Change this", the viewer's arrows and the oldest-first pruning all keep working with no cases of their own. The **client converts to PNG on a canvas before sending**, which does three jobs at once: it normalises whatever a phone hands over (HEIC, JPEG — anything the *browser* can decode) into the one format the gallery stores, so the `^[a-f0-9]{32}\.png$` guard on `/api/image/file/:file` and the ComfyUI upload naming need no widening; it caps the long side at 2048, since a 12-megapixel photo is a pointless base for an img2img latent; and it means the server's only job is reading four big-endian integers out of the IHDR chunk (`pngSize()`) rather than carrying `sharp`, a native dependency on a build that must keep producing linux/arm64 for the Pi. Those dimensions are **parsed, not trusted from the client**, because they are stored and later shown as fact. The body is raw bytes rather than multipart — there is exactly one file and no fields, so a multipart parser would be a dependency bought for nothing — and the caption rides in a header because the body *is* the file. An uploaded picture has no style, sampler or seed, so the details panel says "added from your device" and prints none of them rather than inventing a render that never happened. An id that is no longer there **fails the job** rather than quietly drawing from scratch, and a failed redraw retries *as* a redraw, since "redraw this" and "draw this" produce very different pictures. Strength is three words (light/balanced/strong → 0.45/0.65/0.85, the model author's own ranges) shared by [useImages.ts](client/src/hooks/useImages.ts) and the voice tool, because a language model asked for a denoise number returns 0.5 for everything and a fingertip cannot land 0.65 on a 7" screen. A `KSamplerAdvanced` has no `denoise` input at all and says so instead of silently returning a copy. **Three things about plain img2img were quietly wrong and are worth knowing because each one looked like "the model is bad"**: the source was encoded at its *own* size, so a 3 MP phone photo was handed to a model trained at 1 MP and came back a smeared enlargement — now the source keeps its shape and is fitted to the style's megapixel budget (1 MP at Auto) by an `ImageScale` node `buildGraph` inserts when the numbers differ, and the job carries `sourceWidth/Height` beside the render size so the two are never confused; a KSampler runs `steps × denoise`, so Draft × Light was ~5 sampling steps from a setting that said "draft" — `startImage` now raises a redraw's step count so the ones actually run come to what a fresh render would get (floor 20, a distilled style keeps its own number), and `effectiveSteps()` takes the same discount back off for the estimate; and the prompt is the *only* description the sampler gets of what the source's layout depicts, so "make it night" drew "make it night" in a fox-shaped composition — for an upload (whose "prompt" is a filename) or whenever Improve is on, `composeRedrawPrompt()` in [image-prompt.ts](server/src/image-prompt.ts) *shows the picture* to a vision model (`OLLAMA_VISION_MODEL`, falling back to the improver's model — `gemma4` can see) with the change and this style's `promptGuide`, and gets back the description of the whole result; same never-fail contract as the improver, its time subtracted from the timing sample the same way. Its system prompt is **the user's too** — `visionTemplate` in the same `image-prompter.json`, with the same placeholders, the same cleared-means-reset rule and its own Save/Reset box and expanded preview under Settings → Drawing ("Looking at the picture"), because the description it writes is visible on every redrawn picture's details panel and anyone who can read it will want to change how it is asked for; the fixed user turn (`visionUserMessage()`) and the model that sees the picture are printed beside the preview so the whole conversation can be judged, not half of it. **But img2img cannot do "this exact picture, but X" at all** — it is SDEdit, and the composition is all that survives — which is what **FLUX.1 Kontext dev** is for: `kontextGraph()` (transcribed from ComfyUI's `flux_kontext_dev_basic`, the two-image `ImageStitch` half dropped) is the `wf:flux-kontext-dev` style with **`edits: true`**, the one field that changes the shape of the feature. The source goes into *the graph's own* `LoadImage` rather than being spliced in as a latent, `ReferenceLatent` hands it to the conditioning so the prompt is read as an **instruction** and whatever it doesn't touch is kept, the sampler runs `denoise: 1` so there is no strength to choose, and `FluxKontextImageScale` snaps the source to one of the model's published ~1 MP resolutions (mirrored at queue time by `kontextSize()` so the frame's size text is right; the PNG header is read back after every render regardless, since the graph's own scaling node has the final say). `styleEdits()` gates all of it: `startImage` refuses an editor with no source as a failed job (and the route 400s first, for the panel), `run()` skips both improvers for it — Kontext wants the words verbatim, and a model that expands "make it night" into a scene description turns an edit into a repaint — `/api/image/models` sends `edits` per style, and the Draw panel hides the strength chips, relabels the button "Edit it", clears the seeded prompt (an original's description reads as "repaint all of this" to an editor), swaps the hint from "describe the whole picture" to "say what to change", and offers an "Edit it with … instead" chip on the source card when an editor is installed and not selected. The voice side is `imagePromptGuidance()`: the tool schemas are fixed at module load, so that per-request line is the only place that can say the current style is an editor, that `generate_image` will be refused, and that `redraw_image`'s prompt is now an instruction. It reuses FLUX dev's CLIP-L/T5/VAE, so a box with dev installed needs exactly one more file — `flux1-dev-kontext_fp8_scaled.safetensors` from the ungated `Comfy-Org/flux1-kontext-dev_ComfyUI` — and `weight_dtype` stays `default` because that file is already fp8. **Style selection** covers two different things behind one picker, and has to: an SDXL checkpoint is a `ckpt_name` swapped into the default graph, but **Anima is three files** (a 2B diffusion model, a Qwen-3 0.6B text encoder, a VAE) behind three separate loader nodes with no `ckpt_name` at all. Anima's three published variants — **base v1.0**, **aesthetic v1.1** and **turbo v1.1** — share that graph exactly and differ only in the unet filename and the numbers their author recommends, so `animaGraph()` is one factory rather than three transcriptions; base is still the newest *base*, but aesthetic and turbo have moved on to v1.1. All three keep `euler`/`simple` rather than the author's newer `er_sde` suggestion, because a `sampler_name` the GPU box doesn't have fails as a bare "value not in list" naming a sampler the user never chose. Turbo is distilled — ~10 steps at cfg 1 — so it carries `ignoresQuality`, which takes it out of the draft/standard/high preset entirely (44 steps at cfg 1 is the same picture four times slower) and greys the Quality row with "set by this style", the pattern that row already uses when Advanced's Steps overrides it; Anima ships turbo **two ways and both are real**: `anima-turbo-v1.x` is a separate distilled *checkpoint* (the style), and `anima-turbo-lora-v0.2` is a LoRA that speeds up the base/aesthetic model without swapping it (the Advanced toggle) — which is why those two styles keep `turboHints: ['anima','turbo']` while the turbo *style* declares none, since stacking the LoRA on the distilled checkpoint is how a picture comes out flat. The LoRA is **not** in the `circlestone-labs/Anima` repo, which publishes no `loras/` folder — that absence briefly read as "no such LoRA exists" and got the hints deleted; they are back. Checkpoints come from `huggingface.co/circlestone-labs/Anima` under `split_files/`, ~3.9 GB per variant, and the author's numbers are 30–50 steps at cfg 4–5 for base/aesthetic and 8–12 at cfg 1 for turbo — which is what the graphs carry. So a style id is either a checkpoint filename or `wf:<id>` for a whole graph — built-in (`ANIMA_GRAPH`, transcribed from ComfyUI's own bundled `image_anima_base_v1.json` template, with its frontend subgraph and optional turbo-LoRA switches flattened away since `/prompt` takes a flat graph) or any API-format JSON dropped in `$CACHE_DIR/workflows/`. `buildGraph` patches `ckpt_name` **only** for the checkpoint kind. **Every style is driven by its own published best practice**, because the one-size default was actively wrecking two of them: a workflow style carries `prefixes` (text glued in front of both prompts), its own default `negative`, `optimizations` (text appended AFTER the prompt), `supersedes`, and `promptStyle`. **`prefixes` and `optimizations` are two fields rather than one because position here is published, not a preference**: NoobAI's card calls its quality ladder a "Prompt Prefix" and Anima's calls its own a "recommended positive prefix", and SDXL-family attention weights the front of a prompt most heavily — so quietly relocating a documented prefix to the end would weaken it while looking like a tidy-up. `optimizations` is for what a model wants at the *end* and, more to the point, for whatever the user decides they always want. **Animagine XL 4.0 is the style that makes the field necessary rather than tidy**: its card says in its own words "Add these tags at the end of your prompt" (`masterpiece, high score, great score, absurdres`) and its prompt structure literally ends "...and end with quality enhancement". NetaYume's `best quality` is appended for a different reason — its `prefixes` slot is already taken by the instruction line nothing may come between and `<Prompt Start>`. **Animagine was also being driven three settings wrong at once** until it got a `wf:` entry: as a bare checkpoint it rendered through the default SDXL graph at cfg 8 / `euler` / `normal` where its card asks for cfg 5, 28 steps and `euler_ancestral` — the same "this model is bad" reading NoobAI's entry exists to stop, which is why `sdxlAnimeGraph()` is now one factory serving both. **All four pieces of text this app adds on your behalf — the prefix, the appended booster, the negative and the negative's own prefix — are overridable per style** from Settings → Drawing, stored in `image-params.json` beside the numeric knobs and keyed the same way — for the same reason cfg is per style: a negative is *model-specific text*, so the booru terms NoobAI asks for are wasted on FLUX (which has none at all) and the house English prose is wasted on a tag model, and one global negative would be quietly wrong for whichever model it was not written for. Precedence is request → the user's per-style override → the style's published default → `DEFAULT_NEGATIVE`, and each override is **`string | null`, where `null` and `''` are different answers**: null means "no override, use the card", `''` means an override that is deliberately empty. That distinction is most of what "editable" means for text somebody else wrote — with `'' = fall back`, which is what this was at first, there is no way to say "stop putting `masterpiece, best quality, score_7, safe,` in front of my prompt", because clearing the box would just restore it. Resolution therefore uses `??` and never `||`. The Settings fields show the string actually in effect as their **placeholder** when nothing is overridden — a blank box over a model that has a published negative reads as "there isn't one", and the natural response to that is to type a worse one from memory — and swap that placeholder for "nothing will be added" once overridden, since showing the built-in under an override that switched it off would be the same lie in reverse. Each field grows a "Use the model's own" button only while it is overridden, absent rather than disabled because a dead control on a touchscreen is a tap that looks broken. **`joinPrefix()` is separate from `joinPrompt()`** because the two shipped prefix shapes end differently and only one wants a comma: NoobAI's is a tag list ending `safe,` while NetaYume's ends `<Prompt Start>`, a separator the model was trained on that must NOT be followed by a comma — so a prefix ending in `>` `:` `.` `!` or `?` gets a space and anything else is comma-joined. That only mattered once the field became user-typeable: before, the built-in strings carried their own trailing separator and nothing else could reach it, and hoping a user remembers a trailing space that a text box does not render is not a plan. Both helpers strip commas *and the whitespace around them* from both ends of both halves — the first version stripped a leading comma but left its space, so `, cinematic lighting` appended as `a red fox,  cinematic lighting`, a double space a tag parser reads as an empty tag. All four text fields are resolved in `startImage()` at queue time and `buildGraph` only consumes them, so precedence lives in one place and a render cannot silently re-derive a default over an override. `joinPrompt()` glues the booster on without producing `, ,` or a trailing comma — worth a function because both halves are hand-typed and an empty tag in a booru prompt is one more token the encoder spends on nothing. Two things were simply missing here until the field went in and are worth naming: **Anima had no prefix and no negative at all**, so every Anima render was driven with the house English prose against a model trained on Danbooru and score tags, and **NoobAI's negative was truncated** — missing the `mammal, anthro, furry, ambiguous form, feral, semi-anthro` tail that is exactly the half stopping an anime model drifting anthro on an ambiguous prompt, which shows up as "why did it draw that" rather than as an error. Anima's aesthetic fine-tune takes a *different* pair from base and turbo (no `score_*` on either side), because its card says the quality tags were stripped from its captions and the score tags "push it too hard into slop territory" — the card being specific, not us being clever. Two different kinds of dead negative are distinguished, because the honest answer differs: a style sampled at **cfg 1** (Anima Turbo) still *encodes* its negative and would use it the moment guidance is raised, so it gets a warning on a live field; a style with **no second text encode at all** (FLUX, whose sampler's negative is a `ConditioningZeroOut` of the positive) has nowhere for one to go, so `styleUsesNegative()` — the same identity test `buildGraph` runs before it writes — replaces the box with a sentence saying to describe what you want instead. Black Forest Labs say exactly that, so the empty default there is the vendor's position rather than a gap. One correction worth recording: **Anima's `promptGuide` used to say "plain English, not tags", which was wrong in the expensive direction** — its card says it was trained on Danbooru tags, natural-language captions *and mixtures of the two*, so the guidance now says to keep whichever register the user wrote in, and carries the three rules that card is emphatic about: tags are lowercase with **spaces** not underscores (score tags excepted), an artist tag **must** be written `@artist name` or "the effect will be very weak", and a natural-language prompt wants at least two sentences with a named character's appearance described rather than the name alone. Anima's negatives additionally lead with `nsfw`, which is the one deviation from its card's verbatim string and comes from the same card: its Limitations section says to use safety tags in the positive **and** negative, the positive prefix already carries `safe`, and on a kiosk the assistant draws on unprompted that tag is doing real work — the same reasoning as `safe` in NoobAI's prefix. **NoobAI XL v1.1** is a `wf:` style purely for this — its model card asks for cfg 5–6 and `euler_ancestral`, and the default graph's cfg 8 / `euler` renders it scorched, which reads as "this model is bad" rather than "this model is driven wrong". It also prepends the quality ladder (`masterpiece, best quality, newest, absurdres, highres, safe`) and swaps the house English negative for booru terms. **FLUX.1 dev** is the case that made the *shape* of a style negotiable rather than just its numbers, and `fluxGraph()` (transcribed from ComfyUI's own `flux_dev_full_text_to_image` template) differs from every other graph here in three ways that are all the same fact — it is **guidance-distilled**. Its guidance scale is a conditioning input the model was trained on, not classifier-free guidance over a negative, so the sampler runs at **cfg 1 and must stay there**: raising it switches on true CFG against a negative the model never had, which costs twice the time for a worse picture. The number a FLUX user means by "guidance" lives on a `FluxGuidance` node (3.5 by default), so `buildGraph` sends the Advanced panel's Guidance knob **there** when the style has one and leaves the sampler alone — and `styleDefaults()` and `renderedWith()` read it back from the same place, because an "Auto" that names cfg 1 is a true statement answering the wrong question, and it invites correcting a value that was already right. It has **no negative prompt at all** (the template feeds the sampler a `ConditioningZeroOut` of the positive rather than a second text encode, which also saves a whole T5-XXL pass producing conditioning that gets discarded), so `renderedWith()` records an empty one rather than the house default — the same silent-override lie the per-style params exist to avoid. And it is **two text encoders** through `DualCLIPLoader` with `type: 'flux'`, CLIP-L beside T5-XXL, which is why its `promptStyle` is `prose`: T5 reads sentences, and handing tags to the best prose comprehension on the box is the inverse of the NoobAI mistake. The one deliberate departure from the template is `weight_dtype: 'fp8_e4m3fn'` where it ships `'default'`: the published weights are bf16 and 23.8 GB, which do not fit a 24 GB card alongside the encoder, and ComfyUI's answer — streaming the model from system RAM every render — is not a slower picture but a stalled one, the same reason there is no CPU twin for ComfyUI at all. fp8 casts on load to ~12 GB and is what ComfyUI's own docs recommend at this VRAM; the matching fp8 T5 is paired with it. Every file it `needs` has an **ungated** mirror (`Comfy-Org/flux1-dev`, `comfyanonymous/flux_text_encoders`, and the FLUX autoencoder inside `Comfy-Org/Lumina_Image_2.0_Repackaged`), which matters because the first-party `black-forest-labs` repos are gated and 401 without a logged-in token — a setup step a kiosk has no way to perform. **`supersedes` hides the raw checkpoint** a `wf:` style wraps, since an all-in-one file otherwise appears twice — once as the style and once as the bare filename that renders through the default graph with none of this, the same model quietly set up to fail. **`promptStyle` is the half the tool schema can't carry**: `generate_image`'s argument description is fixed at module load but the selected style is a runtime choice, so `imagePromptGuidance()` appends a line to the system prompt per request — booru tags with the character tag *and* series (`haruno_sakura, naruto_(series)`) for the Danbooru-trained models, plain English for Anima, whose encoder is Qwen-3. That line is what actually unlocks named characters: describing one ("a girl with teal twintails") asks the model to invent a lookalike and never reaches the character it demonstrably knows. A workflow style's `needs` list is **checked against the box before the style is offered** — `missingFiles()` asks each loader node what it actually has (`UNETLoader`/`CLIPLoader`/`VAELoader`, matched on the filename tail so a subfolder still counts) and `/api/image/models` returns a per-style `missing[]`, which the picker greys out and names. That check is the half of `needs` that was missing for a while: the field existed and nothing read it, so a box with only `anima-base-v1.0` still offered Aesthetic and Turbo, and choosing one looked fine, queued fine, and failed twenty seconds later with ComfyUI's bare "value not in list". For the same reason **turbo with no resolvable LoRA now fails the job** instead of rendering without it — dropping the LoRA that was asked for is just as silent an override as substituting the wrong one, and on a box with no LoRAs at all the old behaviour meant the switch did nothing and said nothing; the Advanced panel additionally disables the toggle outright when `listLoras()` comes back empty. **Quality** is `image-quality.json` and is sampling steps *only* — draft/standard/high → 12/26/44. cfg and sampler are deliberately left to whatever the chosen graph specifies, because those are per-model tuning rather than quality: Anima wants cfg 4 where SDXL wants 8, and bending them from a quality button would quietly wreck one of them. Both stores are `image-model.json` and `image-quality.json` in `$CACHE_DIR`, read per request rather than cached — the same shape and reason as the voice-pitch slider in tts.ts: picking a style has to take effect on the *next* picture, not after a restart. `GET /api/image/models` asks ComfyUI itself what is installed (so a name from the picker can never come back as "value not in list"), and `POST /api/image/model` validates against that list before saving. The choice is deliberately shared with the assistant — someone who switches to an anime checkpoint means "draw in this style", and having `generate_image` keep using the realistic one because the request arrived by voice would be absurd: the user picks the style, the assistant picks the subject. Precedence is per-request override → the user's saved choice → `COMFYUI_MODEL` → whatever the workflow itself specifies. `GET /api/image/check` (the ComfyUI half of the Debug tab's connection checks) lives in the image router rather than beside `/api/system/check/elevenlabs` to avoid a require cycle, since image.ts already imports `broadcast()` from routes/system; it reports free VRAM, because "reachable" and "has room to load a checkpoint" are different questions
- **[image-prompt.ts](server/src/image-prompt.ts)** — the **prompt improver**: one model call that rewrites what the user typed into a prompt for the picture model that is about to draw it, behind a switch in the Draw panel (`GET`/`POST /api/image/prompter`, Settings → **Drawing**). Three properties are the whole design, and each is a deliberate *not*-something. It is **not the assistant**: its own model (`OLLAMA_IMAGE_MODEL`, or one named in the store, falling back to `OLLAMA_MODEL`), no tools, `think:false` — the same reasoning as `OLLAMA_GUIDE_MODEL`, since this call happens inside a render that already takes a minute, so a slower better model costs nothing anyone can perceive. It is a **brand new conversation every single time**: two messages built from scratch and thrown away, nothing module-level surviving a call. That is the contract rather than an optimisation waiting to happen — rewriting "a cat in a hat" must not be coloured by the fact that the last picture was a cyberpunk street, and [session.ts](server/src/session.ts)'s continue/maybe/new scoring has no business near it. And it **never fails a render**: every path — dead box, non-200, empty reply, a rewrite that came back 3000 characters or shorter than the request — falls back to the user's own words and carries the reason into the job's `detail`, because failing a picture over an optional nicety would make the switch dangerous to leave on, and "it drew what I typed" and "it silently couldn't reach the model" are indistinguishable from the outside otherwise. **The template is the user's** and lives on the volume in `image-prompter.json`: prompting taste moves faster than this app does. What is *not* theirs to get wrong is the model-specific half — `{{style}}` and `{{guidance}}` are substituted from **`stylePromptGuide()`**, a per-style `promptGuide` taken from each model's published advice exactly as its sampler settings were, so one template yields booru tags with the character tag *and* series in front of NoobAI and a T5 paragraph with no negative in front of FLUX. `promptStyle` is the one-bit version of the same fact and is all the assistant's system prompt needs; this is the long version, because a model asked to write a good prompt for a model cannot do it from "tags" alone. `GET /api/image/prompter` returns the template **and what it expands to for the selected style**, since a template full of placeholders can't be judged in the abstract — that preview is what makes the model-awareness visible rather than a claim. The improver is **off for the voice tools**, explicitly: a spoken `generate_image` prompt was already written by a model holding this style's guidance, so improving it again is one model paraphrasing another for several seconds of extra silence while somebody waits. Its duration is **subtracted from the render's timing sample** before `recordRender()` sees it — left in, the estimator would learn that a style is seconds slower than it is and the bar would drift with a toggle rather than with the GPU, which is the exact failure [image-timing.ts](server/src/image-timing.ts) exists to end. The picture records `promptOriginal` and `improvedBy` only when a rewrite actually happened, so its presence *is* the record; the gallery's `prompt` stays the rewritten one, because that is what the sampler read and what "use as prompt" should hand back
- **[image-params.ts](server/src/image-params.ts)** — the **advanced render knobs** (`GET`/`POST /api/image/params`, Draw → Advanced): megapixels, side alignment, steps, cfg, the turbo LoRA and its strength, and seed mode. **Keyed by style, not global**, for the same reason the quality button was never allowed to touch cfg — Anima wants cfg 4 where SDXL wants 8, so one global value would silently wreck whichever model wasn't the one you tuned for; a style's settings follow the style and switching swaps the whole set. **Every zero means "leave it alone"** (steps 0 → the quality preset, cfg 0 → whatever the graph specifies, megapixels 0 → the fixed orientation sizes), so an untouched panel renders byte-identically to before the file existed — which is also what lets `POST` be a patch that sends one knob per tap. `GET` returns the saved `values`, the `defaults` read live out of that style's own graph (`styleDefaults()` — so a control sitting on "Auto" can *name* the number it defers to) and the installed `loras`; a dead GPU box costs the LoRA list only, not the panel. **Megapixels sets the size, the orientation buttons still set the shape** — `sizeForMegapixels()` solves `w·h = budget` at the requested aspect and snaps to `multipleOf`, which is why one setting covers all three orientations instead of needing nine fixed sizes, and it's how ComfyUI's own Anima template does it. The budget runs to **16 MP** and the multiple to **512** (any value, rounded to a multiple of 8 — that part isn't a preference, it's what the latent space is), both typed rather than picked. `MAX_USER_DIM` is 6144, looser than the `MAX_DIM` guard on *model-supplied* dimensions — the same operator-vs-model distinction `COMFYUI_URL` makes against `isPublicHttpUrl()` — and it is sized so it stays a **guard rather than a second hidden cap**: the longest side any orientation needs at 16 MP is 4896, so the number asked for is the number rendered right up to the ceiling. At the old 2048 someone could set 12 MP and quietly be rendered 8, which is exactly the silent-override failure the per-style store exists to avoid. **Turbo** puts back the switch node that flattening `ANIMA_GRAPH` threw away: `buildGraph` splices a `LoraLoaderModelOnly` in by **rewiring** — whatever fed the sampler's `model` becomes the LoRA's input and the LoRA becomes the sampler's — so it works identically over a `UNETLoader` (Anima), a `CheckpointLoaderSimple` (SDXL) or someone's existing LoRA stack. Model-only rather than `LoraLoader` because a text encoder that isn't CLIP (Anima's is Qwen-3) has no `clip` output to hand it. The LoRA filename is **matched against `listLoras()`, never hardcoded** — it's a file on the GPU box's disk, and a guess fails as a bare "value not in list"; an unresolvable one is *skipped*, since a wrong LoRA silently changes the picture instead of failing. Resolution happens in `run()`, not `startImage()`, which must stay synchronous for the chat tool calling it. Seed mode `fixed` is what makes iterating on one picture possible (change a word, change one thing); `increment` advances the stored value through `advanceSeed()`, in the store module because it's the only thing that knows the last one
- **[downloads.ts](server/src/downloads.ts)** — **why a download is stuck, and what to do**. The tab used to show a state word and a percentage, which names the symptom and answers nothing: "stalled" is not a reason. Every useful answer already existed but was spread across four services — qBittorrent knows the tracker replied `unregistered torrent`, Sonarr knows the import failed because the file was already imported, `/transfer/info` knows the VPN has no forwarded port — and none of them is the one you are looking at. `diagnose()` is the join: one headline, one sentence of what to do, the **actions** that would do it, and the **evidence** it fired on, because a verdict you cannot check is just a different opinion. Rules run in **severity order and the first wins**, so a torrent that is both queued and seedless reports as seedless. `diagnoseStack()` covers what explains several rows at once: a firewalled connection (normal behind a VPN, and why everything crawls), alternative speed limits left on, a disk with less free space than the queue still needs, three or more seedless downloads at once (a connection problem, not three dead releases). The **list uses the cheap verdict** and opening a row upgrades it, because trackers and properties are one qBittorrent call each and the list runs to a hundred rows. Actions map to real endpoints: recheck, reannounce, `setForceStart`, `topPrio`, the *arr's `RefreshMonitoredDownloads` command for an import that never happened, and **`replace`** — blocklist the release so the *arr never grabs that exact file again, search for another, and delete the torrent with its data, which is the compound thing anyone actually wants for a dead release. The tab is two views behind one switch, **Coming** and **Missing**, because the second is the reason most of the first exists. **Missing** ([MissingView.tsx](client/src/components/widgets/PlexWidget/MissingView.tsx), `GET /api/plex/missing`) is what is wanted and absent: every monitored series with a gap, worst first, opening to its seasons and inside those to **every episode with a tick or a gap**. That level is the point — "12 missing" is a number, "S03E04, S03E05 and all of season 6" is something you can act on — and each season carries its own search, since a gap is nearly always a season's worth rather than one file. Counts come from Sonarr's **own per-season statistics** rather than being derived from the episode list, which would be a call per series; the episode list is fetched only when a series is opened. "Missing" means monitored, **aired**, and no file: counting unaired episodes would park every ongoing show in the list permanently, and films not yet released are shown in their own dim "Not out yet" group so their absence from the main list is explained rather than mysterious. Posters come through `GET /api/plex/arr/poster/:kind/:id`, which proxies the *arr's own cached art so the API key never reaches the browser. **Manual search** is Sonarr/Radarr's interactive search in the row for the download it would replace: `GET /torrents/:hash/releases` asks every indexer live (hence the 120 s timeout, and hence not fetching it until asked) and returns what they have, **including the releases the *arr refused and the reason** — the half that explains a queue that keeps grabbing something dead, or an empty one caused by a quality cutoff. Approved first, then by seeders, since a manual search is usually happening *because* the automatic pick had none. `POST /torrents/:hash/grab` sends `{guid, indexerId}`, which is what the *arr's own UI sends, overriding its judgement; `POST /torrents/:hash/search-again` is the ordinary automatic search (`EpisodeSearch`/`MoviesSearch`). All three need the *arr queue row, which is where the episode or movie id comes from — without one there is nothing to search *for*, and the route says so rather than guessing from the torrent name. **Bulk** ([downloads-bulk.ts](server/src/downloads-bulk.ts)) is the point of the verdicts rather than a convenience on top of them: a hundred rows is really five or six situations, and once a group has one answer, applying it a row at a time is just typing. The tab groups by verdict and offers, per group, only the actions **every** row in it accepts — a button that silently skips a third of what it names is worse than no button. It is a background job for the same reason guides and renders are (78 replaces is 78 Sonarr calls plus 78 qBittorrent calls), strictly sequential with a pause between destructive ones because the *arr is a single box and a burst of concurrent deletes is a timeout storm, one run at a time, progress over a `downloads-bulk` SSE frame so a run outlives the panel, and per-item failures collected rather than failing the lot. `refresh-import` is one global command however many rows are selected. The **hashes come from the client**, not from re-deriving the group server-side: the user acted on the rows they were looking at, and a verdict that changed between the render and the tap must not silently widen what gets deleted. `DELETE /api/plex/torrents/:hash` takes `files`, `blocklist` and `search` **separately**, because "I already have this" and "this release is broken" want different combinations; the *arr's queue row is removed **before** the torrent, or it is left orphaned complaining about a download that no longer exists
- **[plex-watch.ts](server/src/plex-watch.ts)** — the **Watch/Play list follows Plex**. Every minute (and a few seconds after the kiosk reports playback) it reads `/status/sessions` — every Plex client, not just the kiosk's player — and makes sure the film or show is in the list (added with the Plex poster, cached through `cacheCover()` with the token in a header) and a show is `in_progress` (a film stays `not_started`: the list's movie states are only that and done). Anything seen in a session is remembered and, once it is no longer playing, checked against Plex's own counters — a film with `viewCount` and no `viewOffset`, a show with `viewedLeafCount >= leafCount` — and ticked `done`. Rows carry the `plexKey` they follow, which both normalizers whitelist. Never undone and never removed. The client's list refetches on the `media` SSE frame
- **[media-stack.ts](server/src/media-stack.ts)** + **[routes/plex.ts](server/src/routes/plex.ts)** + **[routes/plex-tools.ts](server/src/routes/plex-tools.ts)** — the **media stack**: Plex, and around it Sonarr/Radarr (what's on its way), qBittorrent (the torrents themselves), Seerr (asking for something) and Bazarr (subtitles still being hunted). Six clients in one file, all optional, all read from `MEDIA_*` env; `plexEnabled()` gates everything — `PLEX_TOOLS` is empty and the system prompt's PLEX paragraph is omitted without a Plex URL, the same reasoning as `IMAGE_TOOLS` and ComfyUI, and `request_media` / `control_download` are only offered when Seerr / qBittorrent are. The Plex token **never leaves the server**: posters go through `GET /api/plex/img`, and playback through `GET /api/plex/hls/:session/{*rest}`, a proxy over Plex's universal transcoder — `POST /play` starts a session (direct-stream video, transcode audio, mpegts) and stores its query in a Map keyed by a session id, the proxy re-attaches those to `start.m3u8`, rewrites the transcoder's absolute playlist paths to itself, and pipes segments as streams; idle sessions are swept after ten minutes. Playing a **show or season resolves to the next episode** server-side (`nextEpisode`: the one part-watched, else the first unwatched, else the first), so the tap and the voice tool agree. Languages come from Plex's Stream objects (streamType 2 audio / 3 subtitle) over every leaf of a show, fetched in batches of 25 keys per call because a 200-episode show is otherwise 200 round trips; Bazarr's wanted list is matched by normalized title. Torrents are qBittorrent's list **joined to the *arr queues by download hash**, which is how "Frieren.S02E05.1080p…" gets labelled with the show; pause/resume only, never delete — that's a decision for the real UI. Requests are Seerr's search + `POST /request` (a whole show by default, or the seasons named), with Seerr's 1–5 media status mapped to words. **The Library tab is organised the way Plex is**, which is worth knowing because Plex's own apps hide it: a server is a set of **libraries** ("sections" — Movies, Anime, TV Shows), each one folder on disk plus a *scanner* that reads the file and folder names and an *agent* (`tv.plex.agents.movie`/`series`) that fetches the metadata and artwork for what the scanner found. Libraries have no artwork of their own — the tile is four recent posters. Inside one, `GET /api/plex/section/:id` is Plex's `all` endpoint with its own sort keys (`titleSort`, `addedAt`, `originallyAvailableAt`, `audienceRating`, `lastViewedAt`, `random`), its genre filter (`/genre` lists them with ids), and the unwatched flag — which is `unwatched=1` for a film and `unwatchedLeaves=1` for a show, since a show is "unwatched" while any episode is. `/hubs` are the shelves Plex computes per library (continue watching, recently added, start watching, rediscover, more in <genre>, top rated) and are served as-is rather than re-derived. `/folder?parent=` walks the **disk tree** Plex keeps beside the metadata tree (a folder row has no `ratingKey` and a `key` one level down; a file is a real item), which is the "browse by folder" view and the only way to see a season that the agent mis-matched. Collections are an item with children. **Artwork and metadata come from the agent and live on the item**: `thumb` is the poster, `art` the backdrop, `Image[]` names them by type, `UltraBlurColors` are the four corner colours Plex's new apps paint behind a page instead of a blurred backdrop (carried as `colors`), `Role[]` is the cast with headshots on Plex's public CDN (`metadata-static.plex.tv`, loaded directly — no token), `Rating[]` names its source in the badge URI's scheme (`imdb://…`, `rottentomatoes://…`), `Extras` holds the trailer (a `clip` item, playable by key through the same transcoder), and `Related` is the shelves Plex computes per item (similar titles, more from the studio, more with each lead). `toItem(raw, full)` maps the cheap fields always and the long tail (cast, crew, ratings, trailer, related) only on `plexItemFull()`, because a 24-poster grid must not carry 24 casts. The collapsed pill carries a **Play button for "up next"** (the first on-deck item) so where they left off starts from the couch in one tap; it is a `role=button` span rather than a nested button, since the pill is itself a button. The Downloads rows carry Sonarr/Radarr's own `statusMessages`/`errorMessage` as a `note` ("waiting for a better release", "import failed: file already exists"), joined in `arrQueue()` and shown under the row and in the voice tool — the question a stuck row actually raises. Plex's `recentlyAdded` lists the *season* that arrived, so `plexRecentlyAdded()` replaces each with its show, once per show. Voice side: `play_media` (which, for an unwatched film of 95+ minutes that has a trailer, answers with an **offer** instead of playing — the assistant asks "want the trailer first?", keeps listening, and calls again with `mode: trailer|film`; a trailer is a `clip` played through the same transcoder), `whats_on_plex`, `media_languages`, `request_media`, `media_requests`, `download_status`, `control_download`, returning `{kind:'plex'}` display payloads that `openBrowseFromPayload` routes to the player or the panel — **everything reachable by tapping is reachable by asking**, the guide's rule. Rate limits: `/hls`, `/img` and `/poster` ride `tileLimiter`, since an HLS stream is a segment every few seconds and a poster grid is thirty requests, and 60/min would cut a film off mid-scene
- **[routes/stt.ts](server/src/routes/stt.ts)** — `POST /api/stt` → Vosk or Whisper transcription
- **[memory.ts](server/src/memory.ts)** — what the assistant knows about the user, in `memory.json`. Long-term (no expiry, 50 max) holds two `kind`s: `fact` ("the user's name is…") and `preference` — a learned *answer shape* ("when they ask how to get past a part of a game, they want a video"), saved via the `remember_preference` tool. Preferences are injected under their own heading with instructions to **offer, never assume**, so the assistant proposes the format and calls `keep_listening` for a yes/no instead of silently opening a window. Short-term (24h TTL, 30 max) holds the end-of-conversation auto-summaries. Facts carry a **`topic`** (people/food/home/media/games/work/schedule/health/other — the `remember` tool files them, older ones are guessed from their words by `topicOf()`) and can be **`pinned`**, which puts them first and keeps them out of the cap's eviction; `PATCH /api/memory/:id` corrects the wording, re-files or pins one, which is what the Memory tab's tap-to-edit, topic chip and pin do. `formatForPrompt()` injects the lot into every system prompt, facts grouped under their topic headings. `forget` refuses queries under 3 chars or matching more than 3 entries — it's driven by a language model and used to be able to empty the store in one call
- **[session.ts](server/src/session.ts)** — the **last conversation**, kept 12h so a topic can be resumed. The client wipes its history when the assistant hangs up, so the transcript is parked here on the way out. On the first utterance of the *next* conversation, `scoreContinuation()` decides `continue` (replay the old turns as real history) / `maybe` (inject only a one-line recap, flagged as possibly unrelated) / `new` (inject nothing — today's behaviour). The scorer is lexical, not a model call: an LLM classifier would sit in front of every reply on a local Ollama box, the same latency `OLLAMA_THINK=false` exists to avoid. The `maybe` band is what lets a cheap scorer be wrong at the edges. The decision is latched in `chat.ts` for the whole conversation, since the client only ever sends its own turns
- **[guide-activity.ts](server/src/guide-activity.ts)** — the running account of what the guide system is doing, behind Settings → **Guides**. A 300-entry in-memory ring buffer; `note()` is the single place guide progress is written to stdout, and it also broadcasts a `guide-activity` SSE frame and appends to the buffer, so the console line and the on-screen line are the same sentence and can't drift. `GET /api/guides/activity` serves the backlog for a tab opened mid-run (**registered above `GET /:itemId`** — Express matches in order and would otherwise read `activity` as a media-item id). Deliberately not persisted: it's a window onto work in progress, and guides.json already has a writer per section. Why it exists — a run is a dozen model calls and twice as many fetches over minutes, and its only trace was one constantly-overwritten `phase` string; when a chapter came back empty, the answer to *why* (no wiki page, throttled search, model returned nothing twice) was being logged and thrown away
- **[routes/memory.ts](server/src/routes/memory.ts)** — `GET/POST/DELETE /api/memory` (+ `DELETE /api/memory/session`), behind the Settings → **Memory** tab. Memory was previously inspectable only by asking out loud and trusting the answer; this is the window and the off switch
- **[host.ts](server/src/host.ts)** + **[routes/host.ts](server/src/routes/host.ts)** + **[scripts/host/](scripts/host/)** — Settings → **Server**: updating the machine the container runs on. A container can't run apt, fwupd, tailscale or docker on its host, and the usual escape hatches (the docker socket, `--privileged`) are root on the host in all but name and still don't reach apt — so the container talks to the host **over SSH with a key it generates itself** on the volume (`$CACHE_DIR/host/id_ed25519`, made by `ssh-keygen` on first use; the image carries `openssh-client` for it), and the host decides what that key may do: its authorized_keys line is `restrict,command=` pinned to one root-owned script, `scripts/host/touchsphere-host`, which accepts a **fixed list of verbs** (`status`, `apt-refresh`, `apt-upgrade`, `firmware-check`, `firmware-update`, `tailscale-update`, `containers`, `self-update`, `reboot`) and refuses anything else, re-executing itself through a sudoers rule that allows exactly those verbs. A compromised container can install the host's updates or reboot it; it cannot open a shell on it. `scripts/host/install.sh` puts all of that in place from the public key the tab shows, and writes `/etc/touchsphere-host.conf` with the dashboard's checkout and every *other* compose file behind a running container. `status` is one JSON document (OS, uptime, load, disk, reboot-required and `needrestart`'s kernel verdict, pending apt packages from a simulated dist-upgrade, Tailscale version vs `--upstream`, fwupd's cached update list, each compose project's containers, the checkout's commit and how far behind its upstream). Tasks run **one at a time** — apt holds a lock — and stream stdout line by line over the `host-update` SSE event into a 600-line ring buffer (the guide-activity pattern, with `\r` treated as a line break because apt draws progress with it), so the screen shows apt working rather than a spinner. `self-update` is **detached on the host** (`nohup setsid … git pull && docker compose build app && up -d`, logged to `/var/log/touchsphere-self-update.log`) because a container cannot watch itself being replaced; the tab notices the server go away and come back and reloads. `self-update` and `reboot` need `confirm:true`, which the tab only sends on a second tap. Everything 404s without `HOST_UPDATE_SSH`, so the tab is absent rather than empty — the ComfyUI/Plex rule
- **[routes/state.ts](server/src/routes/state.ts)** — `POST /api/state/*` persists media list, mode, lock credential as JSON in `$CACHE_DIR` (Docker volume `/data/cache`)
- **[presence.ts](server/src/presence.ts)** + **[routes/presence.ts](server/src/routes/presence.ts)** + **[scripts/presence/](scripts/presence/)** — **desk presence** from an HC-SR04 ultrasonic module. The sensor is on the **Pi's** GPIO (the kiosk), and the server is another machine, so `presence.py` runs on the Pi as a **user** systemd unit (`install.sh` installs it, and needs **no root**: the `gpio` group covers the pins and `lgpio` ships with the OS — an installer that needed a password could not be re-run on a Pi where sudo prompts. Wanted by `default.target`, since labwc never activates `graphical-session.target`. Wiring is in the script's header; the 5 V ECHO pin **must** go through a divider to 3.3 V or it damages the input), measures twice a second through **lgpio directly** rather than gpiozero — gpiozero's `DistanceSensor` does exactly this but is not installed and needs root to add, and the measurement is twenty lines; Python's tens of microseconds of jitter is millimetres, irrelevant against a threshold most of a metre away. No echo at all is treated as out of range rather than as an error, because that is also what an unwired sensor looks like, and it is said out loud once a minute rather than reported as a confident "away" that is right for the wrong reason, decides "at the desk" with hysteresis (~1.5 s near to arrive, ~20 s far to leave, so a lean-back is not leaving) and POSTs each change plus a 30 s heartbeat to `/api/presence`, optionally under `PRESENCE_TOKEN`. The server keeps the answer, flags a reader that has gone quiet as `stale`, broadcasts a `presence` SSE frame, and adds one `DESK:` line to the system prompt per request. What is done with it is small on purpose: the kiosk **dims after N minutes away** (Settings → Hardware, `presence.json`; any tap lifts it for two minutes so a mis-aimed sensor can never trap someone at a dark screen), `get_device_status` reports it, and nothing locks, logs a timeline or guesses who it is — a distance under a threshold is all the sensor can say
- **[routes/device.ts](server/src/routes/device.ts)** — `GET /api/device` reads `/sys/class/thermal/thermal_zone0/temp` and `/proc/meminfo` (Pi-specific)
- **[routes/weather.ts](server/src/routes/weather.ts)** — current weather + 5-day forecast via OpenWeatherMap; cloud-layers and `GET /api/weather/timeline` via Open-Meteo (keyless). **The timeline is the only source of past weather** — OWM history sits behind a paid One Call 3.0 subscription and 401s on the free key. It returns one contiguous hourly series (2 days back → 5 days ahead) in OWM's units, and drives the map's time scrubber. Note map *imagery* has no such range: RainViewer covers ~2h back plus a 30-min nowcast, OWM cloud tiles are always a live snapshot, so outside that window the overlay is hidden and the badge reads "NO IMAGERY · DATA ONLY" rather than painting current clouds on a past timestamp
- **[routes/tiles.ts](server/src/routes/tiles.ts)** — proxies OWM cloud tile requests (rate-limited separately)
- **[routes/artwork.ts](server/src/routes/artwork.ts)** — cover art for the Watch/Play list. `GET /api/artwork/search?type=&q=` hits TMDB (movies/shows) or IGDB (games); the chosen poster is downloaded once into `$CACHE_DIR/covers` and served by `GET /api/artwork/cover/:file`, so the list renders offline. `state.ts` looks up a cover on add (`autoCover`) and re-caches on `PATCH /api/state/media/:id { coverUrl }` when the user corrects a wrong match. IGDB authenticates via Twitch client-credentials (`IGDB_CLIENT_ID` + `IGDB_CLIENT_SECRET`); both providers are optional — without keys, items fall back to a gradient tile

### Deployment

- **Dockerfile** — 3-stage build: client (Vite), server (tsc), production Alpine image with `espeak-ng` + `su-exec`
- **Caddy** — reverse proxy on :443 with self-signed TLS (required for browser microphone/camera APIs in kiosk)
- **Watchtower** — polls `ghcr.io` and auto-updates the running container
- **CI/CD** — `.github/workflows/docker-publish.yml` builds `linux/amd64` + `linux/arm64` on every push to `main`
- **Kiosk** — the Pi is normally a *display only*: the dashboard runs on another box and the Pi opens it. `scripts/kiosk/install.sh <url>` sets that up — installs TouchKio (Electron, its own fullscreen Chromium, which is what gives the kiosk a microphone and therefore a voice loop, and why the URL must be **https**), writes the URL to `/etc/touchsphere-kiosk.conf`, and installs `touchsphere-kiosk` as a **user** systemd service with `loginctl enable-linger`. A user service rather than a system one because Bookworm runs Wayland and a system unit has to guess at `DISPLAY`/`WAYLAND_DISPLAY` and gets it wrong whenever the compositor changes; a user service starts inside the graphical session and inherits all of it. The runner **waits for the dashboard to answer** before opening the browser (up to 3 min) rather than showing TouchKio's own error page, and exits non-zero if it never does, so systemd retries — the usual cause is the server booting more slowly than the Pi. `scripts/kiosk.sh` + `scripts/touchsphere-kiosk.service` remain for the all-in-one case, where the container runs on the Pi too

## Key Constraints

- **Touch-only UI** — no hover states, all interactions must work with a finger tap
- **No stray zoom** — the same build runs on a phone, where two things zoom the viewport with nothing on screen to explain it. `touch-action: manipulation` is set on `*`, not on `body`: touch-action is not inherited, so on `body` alone a double-tap landing on a button (i.e. every control here) still zoomed. And iOS Safari zooms in whenever a field with a computed font-size under 16px takes focus, which these are by design — and because they also carry `inputMode='none'` no keyboard comes up with it, so the zoom arrives unexplained and stays. `maximum-scale=1` in the viewport meta is what suppresses that; iOS has ignored it for genuine pinch since iOS 10, so the a11y escape hatch survives there
- **ARM64 target** — Docker images must support `linux/arm64` for Raspberry Pi 5; test multi-arch builds before merging
- **Secure context required** — microphone and camera APIs require HTTPS; Caddy provides self-signed TLS even in local dev on Pi
- **Offline-capable voice** — wake-word detection (Vosk) and TTS fallback (espeak-ng) must work without internet
- **State persistence** — app mode, media list, and lock credential survive restarts via server-side JSON in the Docker volume
