# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Client (React/Vite) — run from `client/`
```bash
npm run dev       # Dev server with HMR at http://localhost:5173 (proxies /api/* → localhost:3001)
npm run build     # TypeScript check + Vite production build → client/dist
npm run lint      # ESLint
npm run preview   # Preview production build
```

### Server (Express/Node) — run from `server/`
```bash
npm run dev       # nodemon + ts-node, watches src/index.ts
npm run build     # tsc → server/dist
npm run start     # Run compiled dist/index.js
```

### Docker (from repo root)
```bash
docker-compose up                          # Start app + Caddy + Watchtower
docker-compose --profile local-voice up    # …plus Kokoro + RVC on this box
docker-compose build                       # Multi-platform build (amd64 + arm64)
```

The Kokoro/RVC voice pipeline and ComfyUI image generation are location-independent
(the app reaches them via `KOKORO_URL`/`RVC_URL`/`COMFYUI_URL`). To offload it to a faster machine (typically the Ollama
box), run `docker-compose.voice.yml` there (`--profile gpu` for CUDA via
`docker/rvc/Dockerfile.gpu`, `--profile cpu` otherwise) and point the URLs at it
in `.env`; then start the dashboard box *without* `--profile local-voice`.
ComfyUI rides along in that same file's `gpu` profile and is GPU-only — there is
no CPU twin, because SDXL on the dashboard box is minutes per image, which isn't
a slower fallback but a hang. With `COMFYUI_URL` unset the drawing tools simply
aren't offered.

## Environment Setup

Copy `.env.example` to `server/.env` and fill in:
- `OPENWEATHER_API_KEY` — required for all weather/AQI/tile routes
- `CALENDAR_ICAL_URL` — optional Google Calendar iCal feed
- `DEFAULT_LAT` / `DEFAULT_LON` — recommended (falls back to GeoIP)
- `ELEVENLABS_API_KEY` — optional; falls back to `espeak-ng` on Pi
- `OLLAMA_URL` / `OLLAMA_MODEL` — LLM backend for `/api/chat`
- `YOUTUBE_API_KEY` — optional; makes `play_video` search reliable (falls back to scraping)
- `PORT` — defaults to 3001

## Architecture

### Layout
A full-screen kiosk SPA (720×1280 portrait on Raspberry Pi 5 / 7" touchscreen) with a center 3D particle sphere and four corner widgets. Designed for touch-only interaction at arm's length (minimum 14px, prefer 16–18px fonts).

```
┌──────────────────────────┐
│  [Weather]    [Time]     │   ← top-left blue / top-right yellow (calendar+clock)
│         [Sphere]         │   ← center: Three.js particle sphere
│  [Draw]   [Tasks/Media]  │   ← bottom-left pink / bottom-right green|red
│         [StatusBar]      │   ← mode selector (work/rest/locked)
└──────────────────────────┘
```

- **[components/widgets/](client/src/components/widgets/)** — each widget has collapsed (icon only) and expanded states; `Widget.tsx` is the generic wrapper
- **[hooks/useVoice.ts](client/src/hooks/useVoice.ts)** — core voice loop: SpeechRecognition → `/api/stt` → `/api/chat` → `/api/tts` playback
- **[hooks/useWakeWord.ts](client/src/hooks/useWakeWord.ts)** — offline wake-word via Vosk running in a Web Worker; the wake phrases come from the selected assistant profile
- **[config/assistant.ts](client/src/config/assistant.ts)** — client half of the **selectable assistant** system: the profile table (name, `wakePatterns`, `wakePhrase`, tagline) + a reactive store (`useAssistant`, `setAssistantId`). Four profiles: **Martin** (default), **Jarvis**, **TouchSphere**, **Merlin**. The user picks one in Settings; the id is persisted via `POST /api/state/assistant` so the server's persona + voice follow. The server half (personality + TTS voice) is [server/src/config/assistant.ts](server/src/config/assistant.ts) — keep ids/names in sync. **This is the AI's identity** — the product/app is still "TouchSphere".
- **[components/BrowserOverlay.tsx](client/src/components/BrowserOverlay.tsx)** — full-screen browser window the assistant opens via `open_website` / `play_video` (see [server/src/routes/browse.ts](server/src/routes/browse.ts)). Three bodies: the YouTube embed, a live iframe, or reader mode for the majority of sites that refuse to be framed — with a manual reader ⇄ site toggle, since an iframe can still come back blank. Target lives in [hooks/useBrowse.ts](client/src/hooks/useBrowse.ts) and is opened by `useVoice` at the moment the spoken reply is revealed, so window and voice land together. A video is held (poster, then iframe-API pause/resume) for as long as the assistant has the floor — playback and the voice loop must never share the room
- **[components/widgets/MediaListWidget/GuideView.tsx](client/src/components/widgets/MediaListWidget/GuideView.tsx)** — the **game guide**, full screen, in two layers: a chapter list (nothing but the chapters, each with its kind chip, `x/y` and bar) and, on tapping one, that chapter's own scrolling page of tickable steps with its walkthrough video and prev/next. Steps deliberately never appear in the list — a 12-chapter game is a few hundred of them. A chapter row is **two tap targets**: the body opens it, the trailing circle ticks the whole chapter off where it stands, because picking up a guide for a game you're part-way through means marking several chapters done before reading anything. Inside a chapter, "Mark all done" and "Redo this chapter" sit at the top, above the steps, since both exist precisely to avoid scrolling the steps. The steps themselves are grouped into **collapsible sub-chapters**, and a *finished* part collapses to a single line by default — so a chapter you're half-way through opens on the part you're actually on rather than thirty struck-through steps. Tapping a heading overrides that for good, so the list stops rearranging itself once the user has an opinion. Both layers carry the **same round X at top-right as every expanded widget** — that's the one gesture in this app that already means "done with this screen", and a chapter also keeps a labelled "← Chapters" pill so back-one-level and leave-entirely are never the same guess. The guide previously offered only a small top-*left* arrow, which took two taps to get out of a chapter and sat where nothing else in the app puts its exit Data comes from [hooks/useGuides.ts](client/src/hooks/useGuides.ts): `useGuides()` for the per-game summaries that draw the row/pill bars, `useGuide(itemId)` for the document itself. Both follow the server's `guide` SSE event, which is what makes a generation *fill in while you watch* and a spoken "tick that off" move the bar under your eyes. Note `/api/guides` sends `Cache-Control: no-store`: without it Chrome heuristically reuses the document and those live refetches silently return the old one. Videos are handed to the existing [BrowserOverlay](client/src/components/BrowserOverlay.tsx) via `openBrowse`
- **Overlay stacking** — four portals can be on screen at once, and their z-bands are load-bearing: **9400/9390** ImageOverlay window + backdrop → **9200/9190** BrowserOverlay window + backdrop → **9100** GuideOverlay → **9000** `Widget`'s expanded overlay. A generated picture sits on top of everything because it is the thing that was just asked for and can be asked for while a video is playing. A video opened from inside a chapter must cover the guide, and the guide must cover the Watch/Play list it was opened from. The guide sat at 8900 until it was reported invisible — tapping a game in the *expanded* list rendered the guide under the very widget it was tapped from, so it only appeared once the list was closed. A widget's inner controls (close button at 9999, grab handle at 9500) are inside its own stacking context and can't escape above the guide, so they need no separate handling
- **[components/GuideOverlay.tsx](client/src/components/GuideOverlay.tsx)** + **[hooks/useGuideOverlay.ts](client/src/hooks/useGuideOverlay.ts)** — which guide is on screen. The guide is a top-level overlay rather than a layer inside the media widget because two unrelated things open it: a tap on a game, and the assistant being asked out loud (`show_game_guide`) — and a voice command can't reach into a component's `useState`. Same module-store shape as `useBrowse`, and `openBrowseFromPayload` routes the `guide` and `close` display kinds into it
- **[components/ImageOverlay.tsx](client/src/components/ImageOverlay.tsx)** + **[hooks/useImageOverlay.ts](client/src/hooks/useImageOverlay.ts)** — the full-screen **generated picture**. Same module-store shape and the same reason as the guide overlay: `generate_image` is a voice tool, and a voice command can't reach into a component's `useState`. The distinguishing feature is that **the frame goes up before the picture exists** — a render is ten to thirty seconds and the overlay opens at the moment the spoken reply is revealed, so the empty frame with its phase text *is* the feedback; the alternative is half a minute of silence after "drawing that for you now". `useImageJob()` follows one render to completion from **two** sources, and needs both: the `image` SSE event, plus a `GET /api/image/job/:id` on mount, because the display payload and the SSE frame race — on a re-show or a page reload every frame for that job is already in the past and the overlay would sit on "drawing" forever for a picture that finished before it opened. The progress bar is determinate only once the server has a previous render to compare against, and is capped below full: a bar parked at 100% while nothing happens is worse than no bar. `openBrowseFromPayload` routes the `image` kind into it, **above** its own `^https?://` guard — a picture that is still being drawn has no url at all, and a finished one carries a relative `/api/image/file/…` path that the guard would drop. Once the picture exists the frame also carries the two things anyone does with one, both of them here rather than in the gallery grid because looking at a render full size is the moment you decide it's nearly right: **‹ / › arrows** over the image, and **"Use as prompt"**. The arrows read the gallery from a `GET /api/image` the overlay makes itself — it is opened from three places (a thumbnail, a queue row, a spoken `generate_image`) and only one of those has the list to hand — refetched when a render reports `ready`, since the picture being watched joins the list at the moment it lands; a stored image keeps the id of the job that drew it, so one id addresses both halves. They are **absent, not disabled**, at either end, because a dead arrow on a touchscreen is a tap that looks broken. "Use as prompt" writes into **[useImagePrompt.ts](client/src/hooks/useImagePrompt.ts)**, which is where the Draw panel's compose field now lives: the overlay is a portal at the top of the tree and cannot reach into `ImageExpanded`'s `useState`, the same problem `useBrowse` and `useGuideOverlay` solve the same way. It also raises an `onDrawPanelRequest` event App.tsx subscribes to, because filling a field nobody can see is not reuse — the corner has to come up on it. Side effect worth having: the draft now survives closing the panel. The prompt caption itself carries `.selectable-text`, which opts it out of the app-wide "a tap is never a text selection" rule and puts `-webkit-touch-callout` back, so a long press on a phone can lift one phrase out of it; the buttons cover the whole string, which is the only thing the kiosk can manage
- **[components/widgets/ImageWidget/](client/src/components/widgets/ImageWidget/)** + **[hooks/useImages.ts](client/src/hooks/useImages.ts)** — the bottom-left **Draw** corner: the tap half of `generate_image`. The Draw button is **not gated on the GPU being busy** — it reads "Add to the queue" instead, and the **queue strip** below it lists what is waiting in draw order: the live one with the server's own phase text, the rest numbered, each with an × that drops it (the guide's two-tap-targets-per-row split — the body opens the full-screen frame to watch it, the × removes it). It is absent entirely when the GPU is idle, since an empty list headed "Queue" is a permanent reminder of a feature nobody is using. The collapsed pill reads "Drawing… +3 queued", because "still going" and "still going, three to come" are different answers to the only question someone walking past has. Same job engine, same store, same full-screen viewer, so a picture is identical however it was asked for, and the corner pill reads "Drawing…" for a render the *assistant* started. The Style row lists the checkpoints ComfyUI reports and is hidden when there is only one — one installed model is not a decision. It's a horizontal scroller rather than a `<select>` because a native dropdown opens an OS popup TouchKio renders badly. `enabled` is **re-polled every 30s while it is false**, and only while false: it used to be fetched once at mount, which latched the panel on "isn't reachable" through both of the races that actually happen on this hardware — the Pi booting before the server, and the GPU box being switched on hours later — on a device with no keyboard to reload it with. **[AdvancedPanel.tsx](client/src/components/widgets/ImageWidget/AdvancedPanel.tsx)** is the tuning half — the knobs in [image-params.ts](server/src/image-params.ts), collapsed by default because Style and Quality cover almost every session and a kiosk panel that opens on nine controls is one nobody reads. Its closed header lists whatever is actually overridden, since the failure mode of a collapsed panel is forgetting what you left inside it (and the Quality row dims itself and says "overridden" when Steps is set, so a preset that isn't in effect can't look like it is). Numbers are **−/+ steppers around a typed field, never sliders** — a fingertip can't land 0.05 on a 7" screen. The steppers are for nudging; the middle of every row is a real input that opens the **number pad** ([TouchKeyboard](client/src/components/TouchKeyboard.tsx) with `numeric`, a dialler layout rather than the letter board), because eight taps of + is not a way to ask for 96 steps and every knob here has a value somebody eventually knows exactly. Each row keeps its one-tap "Auto" to get back out — and clearing the field does the same thing, since the Auto text is the placeholder — and stepping *up* out of Auto lands on the control's minimum rather than on one step (cfg 0.5 is a value no model wants). The chip rows (megapixels, align-to) are **shortcuts, not the range**: `LIMITS` in useImages.ts mirrors the server's bounds so a typed value is clamped identically on both sides, and each label states its range, because a field that accepts 400 steps and then shows 150 without saying so reads as the panel losing the setting. Since the knobs are per style, the loader effect carries a cancelled guard that is load-bearing rather than hygiene: tapping through three styles fires three requests, and the slowest one winning would leave the panel describing a style you aren't on — which the next tap would then save *against* the one you are
- **[hooks/useServerEvents.ts](client/src/hooks/useServerEvents.ts)** — one shared `EventSource` on `/api/system/events` with `subscribe(event, cb)`. The restart signal, guide progress (`guide`) and the guide activity feed (`guide-activity`) all ride it; a per-hook EventSource would cost the Pi a held-open request and a heartbeat per widget
- **[hooks/useGuideActivity.ts](client/src/hooks/useGuideActivity.ts)** + the **Guides** tab in [SettingsPanel.tsx](client/src/components/SettingsPanel.tsx) — what the guide researcher is doing, in three blocks: what's generating right now (phase + bar), every guide on disk with its status, and the activity feed itself (tap a guide to filter the feed to it). One GET for the backlog plus the SSE event for everything after, merged on the server's monotonic entry id so a frame arriving mid-fetch can't land twice
- **[components/TouchKeyboard.tsx](client/src/components/TouchKeyboard.tsx)** + **[components/TouchInput.tsx](client/src/components/TouchInput.tsx)** + **[components/touchTextEdit.ts](client/src/components/touchTextEdit.ts)** + **[components/keyboardLayouts.ts](client/src/components/keyboardLayouts.ts)** — the on-screen keyboard. The kiosk has no physical one and the native IME is suppressed everywhere (`readOnly` + `inputMode='none'`), so this is the **only** way text is typed on the device. It used to be append-only — every key did `value + char`, ⌫ did `slice(0, -1)` — which made the caret a fiction: no fixing a typo mid-sentence, and clearing a long prompt meant forty taps. Every edit now happens at the target element's **real selection**, passed in as `targetRef`, and that one change turns on three things at once: tap to put the caret anywhere and type there, drag / double-tap / long-press to select a run, and type or ⌫ over a selection to replace or bulk-delete it. **Selecting was already native behaviour on a `readOnly` input — it was simply never being read.** Two pieces of machinery make it hold: a `useLayoutEffect` that restores the caret after every controlled re-render (React rewrites the whole value and the browser's answer is to drop the caret at the end, which would defeat the file on every keystroke), and a document-level `selectionchange` listener, the only event that covers caret moves inside a form control from tap, drag and our own edits alike. `targetRef` is optional and its absence degrades to the old append-only behaviour — honest rather than tidy, since a caret nobody can see or move is worse than none. There is deliberately **no toolbar of caret buttons**. There was one — undo, four arrows, select-all, copy, paste — and it was the wrong answer to "let me move around the text": arrow keys on a touchscreen are worse than the thing they replaced, and the row sat between the field and the letters. Putting the caret somewhere is a **tap in the field**, which is why `TouchInput` is **not `readOnly`** — it was, to keep the native IME away, but Chromium paints no caret at all in a readonly field, so tapping into the middle of a prompt moved an invisible caret and read as the tap doing nothing. `inputMode='none'` carries that job alone; the trade is that a physical keyboard can type straight in, which is why the field keeps a real `onChange` (and is a feature on a desktop browser). On top of that: hold-⌫ to repeat, double-tap ⇧ for caps lock, and a **`numeric` dialler pad** for number fields — its own return rather than another row variant, because nothing about the letter board applies (no ⇧, no 123/ABC, no space) while caret, selection, undo and ⌫-repeat are all the shared code. Clipboard tries `navigator.clipboard` and falls back to a module-level string, because a kiosk has nobody to answer a permission prompt. The pure text rules live in [touchTextEdit.ts](client/src/components/touchTextEdit.ts) — `insertAt` / `deleteBack` / `caretTarget` / `ordered` — split out of the component so caret arithmetic can be reasoned about and exercised without a DOM, which matters more here than usual: on a device with no physical keyboard, a caret bug is not something the user can type their way out of. `deleteBack` steps back two code units over a surrogate pair so ⌫ can't leave half an emoji, and returns null (not a no-op edit) at position 0 so held-⌫ doesn't fill the undo stack. **The key layouts follow iOS**, in two shapes picked by viewport width: the **iPhone** board (ten columns, ⇧ and ⌫ flanking `zxcvbnm`, `asdfghjkl` inset half a key each side) below `TABLET_MIN_WIDTH`, and the **iPad** board (⌫ on the end of row 1, `return` on row 2, `,` and `.` joining the bottom letter row, ⇧ at *both* ends, taller keys) at 768px and up. The point is muscle memory, not looking Apple-ish — these are the positions a thumb already expects, so the `123` / `#+=` pages carry iOS's own character sets, and the iPad board reuses the iPhone's sets rather than Apple's slightly different iPad ones, because punctuation that moves between two devices the same person uses is worse than punctuation one row off Apple. **Width, not user-agent**: it is the thing that actually decides whether eleven keys fit, it follows an iPad rotating with nothing to listen for, and it puts the 720px-wide Pi on the phone board without a special case. Layouts are data (`KeyDef[][]`, a `w` flex weight per key) rendered by one `renderKey`, and **every row of a board sums to the same weight** — 10 on the phone, `ROW_UNITS` (12) on the tablet — so a letter key is the same width on all three rows; `unevenRows()` exists to assert that rather than eyeball it, and it caught exactly that bug on the tablet board. The one deliberate exception is iOS's own: the phone's punctuation row is five wide keys, not ten, so those carry an explicit 1.25 weight to still total 10. The phone's bottom row makes **two deliberate departures from iOS**, both fixes rather than decoration: `,` and `.` **flank the space bar** (on an iPhone the comma is two taps away on the `123` page — fine for a text message, bad where the longest thing anyone types is a comma-separated image prompt; the tablet board doesn't need it, `,` and `.` are already on its letter row), and **nothing that commits sits next to space** — iOS's single `return` has to be two keys here (`↵` types a newline, `Done` closes), and the first version put `↵` immediately right of the space bar where it was hit by accident constantly. Both now sit past `.` at the far end, so the keys either side of space are punctuation and a mis-tap costs a character, not the field. TouchInput additionally scrolls its field into view on open — the keyboard covers the bottom third of the screen and half this app's fields live down there

### Backend (`server/src/`)

- **[index.ts](server/src/index.ts)** — Express 5 app; Helmet security headers (CSP disabled for Vite), rate limiting (60/min data, 600/min tiles), CORS, request timing logs
- **[routes/chat.ts](server/src/routes/chat.ts)** — `POST /api/chat` → Ollama LLM with conversation history; the system-prompt personality is built per-request from the selected assistant profile ([config/assistant.ts](server/src/config/assistant.ts) → `getSelectedProfile()`). `ASSISTANT_NAME` env seeds the default profile. The client sends `newConversation: true` on the opening utterance after a wake word — that's the only turn on which the same-topic-or-new decision runs (see [session.ts](server/src/session.ts))
- **[config/assistant.ts](server/src/config/assistant.ts)** — server half of the selectable-assistant system: per-profile `persona` (chat personality) + `elevenVoiceId`/`espeakVoice` (TTS). Reads the selected id from `assistant.json` in `$CACHE_DIR`; consumed by chat.ts (persona) and tts.ts (voice)
- **[routes/browse.ts](server/src/routes/browse.ts)** — the assistant's **show-it-on-screen** half. `web_search`/`web_fetch` only let her *talk* about what she found; the `open_website` and `play_video` tools defined here resolve a target and return a `display` payload on the chat reply, which the client renders in [BrowserOverlay](client/src/components/BrowserOverlay.tsx). Resolution is server-side because it needs the network: YouTube search (Data API when `YOUTUBE_API_KEY` is set, otherwise `ytInitialData` off the results page), a DuckDuckGo-HTML fallback for when the model passes a query instead of a URL, and an up-front embeddability probe — most sites send `X-Frame-Options`/`frame-ancestors` and would render as a blank iframe, so those are flagged for reader mode instead. `GET /api/browse/page?url=` serves that reader extraction. Model-supplied URLs are checked against loopback/LAN ranges before any fetch
- **[guides.ts](server/src/guides.ts)** + **[guide-generator.ts](server/src/guide-generator.ts)** + **[routes/guides.ts](server/src/routes/guides.ts)** — **game guides**: one researched, tickable walkthrough per game, organized the way that game's own community organizes it. The store is `guides.json` in `$CACHE_DIR`, keyed by `MediaItem.id` and deliberately *not* folded into `media.json` — that file has two non-atomic writers and a field-whitelisting normalizer that has already destroyed a column once. Every array in a guide is model-generated, so the store caps and re-validates on both read and write, quarantines a corrupt file instead of overwriting it, and writes atomically (the `memory.ts` pattern). Generation is a background job: `startGuide()` writes a `generating` skeleton and returns, so the assistant can answer in one breath while the work outlives the conversation. It is **overview first, then detail, at every level** — for one reason: a local model asked for a long answer doesn't answer badly, it stops partway, and half a JSON object parses as nothing, so no call is ever asked for much at once. Stage 1 is one call for the section list (dungeons/chapters, then collectibles and side quests) plus which sections count toward 100%. Stage 2a is one call per section for its steps **as bare one-line strings, no explanations**, already divided into the chapter's own **sub-chapters** ("Getting there", "Boss: Odolwa") — saved and broadcast at once, so the chapter is a working tickable checklist from that moment. A sub-chapter is a `group` label on `GuideStep`, not a nested array: consecutive steps sharing a group *are* that sub-chapter, and the chapter page derives its headings, per-part counts and collapse state from those runs. The steps stay one flat ordered list because the 1..n numbering the detail pass keys notes to, both progress bars, tick-one-step, tick-a-chapter and `carryTicks` all walk `section.steps` — nesting would fork every one of them into a two-shape traversal for something the UI can group on its own. A guide written before sub-chapters existed, or by a model that ignores them, is one untitled run and renders as the plain list it always was. Stage 2b walks those steps in batches of `DETAIL_BATCH` (8), one call per batch, asking only for the note on each, patched into the stored guide **by step id** (the chapter has been on screen and tickable since 2a — rewriting the array would un-tick what the player ticked meanwhile). Replies are keyed by the step number sent in the batch and numbers outside it are dropped wholesale, because a model that renumbers from 1 would otherwise smear one batch's notes across another's steps. The guide is saved and SSE-broadcast throughout, so a late failure costs the explanations, not the chapter. This replaced a single per-section call asking for 30 steps *with* notes from 26k chars of research, which routinely ran past the timeout or truncated — landing as an empty chapter. Research happens here rather than through the chat tool loop because that loop truncates tool results at 8k chars and caps at 5 rounds. A section that fails is marked failed and the rest continue; a restart mid-job is swept by `sweepInterrupted()` at boot rather than leaving a permanent spinner — to `ready` with the unfinished chapters flagged when anything survived, `failed` only when nothing did, because failing a whole document over two bad chapters points the user at a full rebuild that costs them every ticked box. **`OLLAMA_GUIDE_NUM_CTX` (default 16384) is load-bearing**: Ollama defaults `num_ctx` to 4096 and discards the overflow from the *front* of the prompt, which is where the research notes are — left at the default the model writes each section from instructions with the evidence sheared off, which reads as "the guide has no detail". **A single section can be re-researched on its own** (`regenerateSection`, `POST /api/guides/:itemId/sections/:sectionId/regenerate`, tool `regenerate_guide_chapter`), leaving every other chapter and its ticks alone; `carryTicks` matches steps by normalized text so a rewrite keeps the boxes that survive it. Voice side: `create_game_guide` / `get_game_guide_progress` / `check_off_guide_step` in [dashboard-tools.ts](server/src/routes/dashboard-tools.ts), and the screen-driving half in [routes/guide-view-tools.ts](server/src/routes/guide-view-tools.ts) — `show_game_guide` (full screen, optionally straight to a chapter named or numbered), `list_guide_chapters`, `play_guide_video`, `check_off_guide_chapter`, `regenerate_guide_chapter`, `delete_game_guide`, `close_screen`. Those return a `display` payload like the browse tools, so **everything reachable by tapping is reachable by asking**. `pushGuide` in [guide-events.ts](server/src/guide-events.ts) is the one place that broadcasts a change (generator, voice tools and the REST route all call it; it lives on its own to keep those three from importing each other)
- **[research.ts](server/src/research.ts)** — where guide content comes from, **wiki-first**. Scraped search engines answer a burst of queries with a CAPTCHA and one guide fires a dozen, so the primary source is the game's own wiki through the MediaWiki API: no key, no throttling, clean plain text, and — the real point — a wiki's article structure *is* how that community organizes the game (`communityTableOfContents()` feeds those headings into the outline prompt). The wiki host is discovered by probing slug candidates against fandom.com/wiki.gg (`zelda`, `hollowknight`, `celestegame`…). Two per-farm quirks are handled: `prop=extracts` isn't installed on every Fandom wiki, so those fall back to rendered HTML through the same readability pass reader mode uses, and Wikimedia serves `api.php` under `/w/`. Wikipedia is the next fallback, and only then the open web (hosted search when `OLLAMA_API_KEY` is set, DuckDuckGo HTML otherwise)
- **[routes/tts.ts](server/src/routes/tts.ts)** — `GET /api/tts?text=` → ElevenLabs WAV or `espeak-ng` fallback
- **[image.ts](server/src/image.ts)** + **[routes/image.ts](server/src/routes/image.ts)** + **[routes/image-tools.ts](server/src/routes/image-tools.ts)** — **image generation** through ComfyUI. Location-independent exactly like the voice pipeline — the app only ever talks HTTP, so `COMFYUI_URL` decides where it runs, and in practice that's the GPU box (`docker-compose.voice.yml` starts ComfyUI under the same `gpu` profile as Kokoro and RVC). **The one structural difference from TTS is that there is no fallback**: the voice chain always has espeak underneath it, so a dead GPU box costs an assistant her voice, not her ability to speak — there is no espeak for pictures. So `IMAGE_TOOLS` is **empty unless `COMFYUI_URL` is set**, and the system prompt's DRAWING paragraph is omitted with it; a model that can see a `generate_image` tool will cheerfully promise a picture before discovering there's no GPU behind it. Generation is a background job for the same reason guides are — a cold ComfyUI pays 20–40s loading a checkpoint into VRAM before it draws a step, and the assistant can't hold the conversation open that long — so `startImage()` registers the job, returns, and reports over the existing `image` SSE event. Jobs are **drawn one at a time but may be queued** — `startImage()` appends to a serial promise chain, `pendingJobs()` reads it back in draw order, and `MAX_QUEUED` (8) caps it. One at a time because two SDXL renders on one card don't go twice as fast, they thrash VRAM; queued because asking for four pictures is one thought, and the alternative was standing at the kiosk for ninety seconds between them. A full queue is refused by **returning an already-`failed` job rather than throwing**, so the REST route and the chat tool get one shape back and neither grows an error path of its own (the route also 429s first, so the panel can print the reason under the button the finger is on). `cancelJob()` drops a **queued** job only — the promise link can't be unlinked, so it marks the job `cancelled` and `run()` returns on that mark; a render already on the GPU is seconds from existing and abandoning it would waste work that is already paid for, while what a mis-tap actually produces is the four behind it. Finished jobs are pruned past `MAX_TRACKED_JOBS` (40) — this Map lives in a process that runs for months and the queue makes entries arrive in bursts. `GET /api/image/queue` is the catch-up half (SSE only carries what happens from now on) and `POST /api/image/job/:id/cancel` the other end; the client keeps its own copy of the queue from `image` frames and re-orders it by the `queuedAt` on the wire, because a frame is pushed when **one** job changes and every other job's position moves when the one in front of it finishes. `/prompt` takes ComfyUI's **API-format** export (a flat map of node id → `{class_type, inputs}`), *not* what the ordinary Save button writes — feeding it the latter is the single most common way this fails and it fails with a bare 400, so `baseGraph()` detects the UI shape and says which export to use. The prompt, size and seed are patched in **by node class, not by node id**, so a workflow someone exported themselves keeps working (their KSampler is rarely node `3`); the two `CLIPTextEncode` boxes are the interesting case — nothing in either node says which is the negative one, so they're resolved by following the sampler's own `positive`/`negative` links, which is the only place that distinction exists. A custom graph goes at `$CACHE_DIR/workflows/txt2img.json`, on the volume so it survives a rebuild. Finished PNGs are written atomically into `$CACHE_DIR/images` and served by `GET /api/image/file/:file` — the artwork.ts cover pattern, with one addition: **the store is capped and pruned oldest-first**, because unlike cover art (bounded by the length of the Watch/Play list) generated images grow without limit on a volume that lives on the Pi. `COMFYUI_URL` deliberately bypasses `isPublicHttpUrl()` — that guard exists for *model-supplied* URLs, and this is operator config pointing at a tailnet address, exactly as `RVC_URL` is. **Style selection** covers two different things behind one picker, and has to: an SDXL checkpoint is a `ckpt_name` swapped into the default graph, but **Anima Base v1 is three files** (a 2B diffusion model, a Qwen-3 0.6B text encoder, a VAE) behind three separate loader nodes with no `ckpt_name` at all. So a style id is either a checkpoint filename or `wf:<id>` for a whole graph — built-in (`ANIMA_GRAPH`, transcribed from ComfyUI's own bundled `image_anima_base_v1.json` template, with its frontend subgraph and optional turbo-LoRA switches flattened away since `/prompt` takes a flat graph) or any API-format JSON dropped in `$CACHE_DIR/workflows/`. `buildGraph` patches `ckpt_name` **only** for the checkpoint kind. **Quality** is `image-quality.json` and is sampling steps *only* — draft/standard/high → 12/26/44. cfg and sampler are deliberately left to whatever the chosen graph specifies, because those are per-model tuning rather than quality: Anima wants cfg 4 where SDXL wants 8, and bending them from a quality button would quietly wreck one of them. Both stores are `image-model.json` and `image-quality.json` in `$CACHE_DIR`, read per request rather than cached — the same shape and reason as the voice-pitch slider in tts.ts: picking a style has to take effect on the *next* picture, not after a restart. `GET /api/image/models` asks ComfyUI itself what is installed (so a name from the picker can never come back as "value not in list"), and `POST /api/image/model` validates against that list before saving. The choice is deliberately shared with the assistant — someone who switches to an anime checkpoint means "draw in this style", and having `generate_image` keep using the realistic one because the request arrived by voice would be absurd: the user picks the style, the assistant picks the subject. Precedence is per-request override → the user's saved choice → `COMFYUI_MODEL` → whatever the workflow itself specifies. `GET /api/image/check` (the ComfyUI half of the Debug tab's connection checks) lives in the image router rather than beside `/api/system/check/elevenlabs` to avoid a require cycle, since image.ts already imports `broadcast()` from routes/system; it reports free VRAM, because "reachable" and "has room to load a checkpoint" are different questions
- **[image-params.ts](server/src/image-params.ts)** — the **advanced render knobs** (`GET`/`POST /api/image/params`, Draw → Advanced): megapixels, side alignment, steps, cfg, the turbo LoRA and its strength, and seed mode. **Keyed by style, not global**, for the same reason the quality button was never allowed to touch cfg — Anima wants cfg 4 where SDXL wants 8, so one global value would silently wreck whichever model wasn't the one you tuned for; a style's settings follow the style and switching swaps the whole set. **Every zero means "leave it alone"** (steps 0 → the quality preset, cfg 0 → whatever the graph specifies, megapixels 0 → the fixed orientation sizes), so an untouched panel renders byte-identically to before the file existed — which is also what lets `POST` be a patch that sends one knob per tap. `GET` returns the saved `values`, the `defaults` read live out of that style's own graph (`styleDefaults()` — so a control sitting on "Auto" can *name* the number it defers to) and the installed `loras`; a dead GPU box costs the LoRA list only, not the panel. **Megapixels sets the size, the orientation buttons still set the shape** — `sizeForMegapixels()` solves `w·h = budget` at the requested aspect and snaps to `multipleOf`, which is why one setting covers all three orientations instead of needing nine fixed sizes, and it's how ComfyUI's own Anima template does it. The budget runs to **16 MP** and the multiple to **512** (any value, rounded to a multiple of 8 — that part isn't a preference, it's what the latent space is), both typed rather than picked. `MAX_USER_DIM` is 6144, looser than the `MAX_DIM` guard on *model-supplied* dimensions — the same operator-vs-model distinction `COMFYUI_URL` makes against `isPublicHttpUrl()` — and it is sized so it stays a **guard rather than a second hidden cap**: the longest side any orientation needs at 16 MP is 4896, so the number asked for is the number rendered right up to the ceiling. At the old 2048 someone could set 12 MP and quietly be rendered 8, which is exactly the silent-override failure the per-style store exists to avoid. **Turbo** puts back the switch node that flattening `ANIMA_GRAPH` threw away: `buildGraph` splices a `LoraLoaderModelOnly` in by **rewiring** — whatever fed the sampler's `model` becomes the LoRA's input and the LoRA becomes the sampler's — so it works identically over a `UNETLoader` (Anima), a `CheckpointLoaderSimple` (SDXL) or someone's existing LoRA stack. Model-only rather than `LoraLoader` because a text encoder that isn't CLIP (Anima's is Qwen-3) has no `clip` output to hand it. The LoRA filename is **matched against `listLoras()`, never hardcoded** — it's a file on the GPU box's disk, and a guess fails as a bare "value not in list"; an unresolvable one is *skipped*, since a wrong LoRA silently changes the picture instead of failing. Resolution happens in `run()`, not `startImage()`, which must stay synchronous for the chat tool calling it. Seed mode `fixed` is what makes iterating on one picture possible (change a word, change one thing); `increment` advances the stored value through `advanceSeed()`, in the store module because it's the only thing that knows the last one
- **[routes/stt.ts](server/src/routes/stt.ts)** — `POST /api/stt` → Vosk or Whisper transcription
- **[memory.ts](server/src/memory.ts)** — what the assistant knows about the user, in `memory.json`. Long-term (no expiry, 50 max) holds two `kind`s: `fact` ("the user's name is…") and `preference` — a learned *answer shape* ("when they ask how to get past a part of a game, they want a video"), saved via the `remember_preference` tool. Preferences are injected under their own heading with instructions to **offer, never assume**, so the assistant proposes the format and calls `keep_listening` for a yes/no instead of silently opening a window. Short-term (24h TTL, 30 max) holds the end-of-conversation auto-summaries. `formatForPrompt()` injects the lot into every system prompt. `forget` refuses queries under 3 chars or matching more than 3 entries — it's driven by a language model and used to be able to empty the store in one call
- **[session.ts](server/src/session.ts)** — the **last conversation**, kept 12h so a topic can be resumed. The client wipes its history when the assistant hangs up, so the transcript is parked here on the way out. On the first utterance of the *next* conversation, `scoreContinuation()` decides `continue` (replay the old turns as real history) / `maybe` (inject only a one-line recap, flagged as possibly unrelated) / `new` (inject nothing — today's behaviour). The scorer is lexical, not a model call: an LLM classifier would sit in front of every reply on a local Ollama box, the same latency `OLLAMA_THINK=false` exists to avoid. The `maybe` band is what lets a cheap scorer be wrong at the edges. The decision is latched in `chat.ts` for the whole conversation, since the client only ever sends its own turns
- **[guide-activity.ts](server/src/guide-activity.ts)** — the running account of what the guide system is doing, behind Settings → **Guides**. A 300-entry in-memory ring buffer; `note()` is the single place guide progress is written to stdout, and it also broadcasts a `guide-activity` SSE frame and appends to the buffer, so the console line and the on-screen line are the same sentence and can't drift. `GET /api/guides/activity` serves the backlog for a tab opened mid-run (**registered above `GET /:itemId`** — Express matches in order and would otherwise read `activity` as a media-item id). Deliberately not persisted: it's a window onto work in progress, and guides.json already has a writer per section. Why it exists — a run is a dozen model calls and twice as many fetches over minutes, and its only trace was one constantly-overwritten `phase` string; when a chapter came back empty, the answer to *why* (no wiki page, throttled search, model returned nothing twice) was being logged and thrown away
- **[routes/memory.ts](server/src/routes/memory.ts)** — `GET/POST/DELETE /api/memory` (+ `DELETE /api/memory/session`), behind the Settings → **Memory** tab. Memory was previously inspectable only by asking out loud and trusting the answer; this is the window and the off switch
- **[routes/state.ts](server/src/routes/state.ts)** — `POST /api/state/*` persists media list, mode, lock credential as JSON in `$CACHE_DIR` (Docker volume `/data/cache`)
- **[routes/device.ts](server/src/routes/device.ts)** — `GET /api/device` reads `/sys/class/thermal/thermal_zone0/temp` and `/proc/meminfo` (Pi-specific)
- **[routes/weather.ts](server/src/routes/weather.ts)** — current weather + 5-day forecast via OpenWeatherMap; cloud-layers and `GET /api/weather/timeline` via Open-Meteo (keyless). **The timeline is the only source of past weather** — OWM history sits behind a paid One Call 3.0 subscription and 401s on the free key. It returns one contiguous hourly series (2 days back → 5 days ahead) in OWM's units, and drives the map's time scrubber. Note map *imagery* has no such range: RainViewer covers ~2h back plus a 30-min nowcast, OWM cloud tiles are always a live snapshot, so outside that window the overlay is hidden and the badge reads "NO IMAGERY · DATA ONLY" rather than painting current clouds on a past timestamp
- **[routes/tiles.ts](server/src/routes/tiles.ts)** — proxies OWM cloud tile requests (rate-limited separately)
- **[routes/artwork.ts](server/src/routes/artwork.ts)** — cover art for the Watch/Play list. `GET /api/artwork/search?type=&q=` hits TMDB (movies/shows) or IGDB (games); the chosen poster is downloaded once into `$CACHE_DIR/covers` and served by `GET /api/artwork/cover/:file`, so the list renders offline. `state.ts` looks up a cover on add (`autoCover`) and re-caches on `PATCH /api/state/media/:id { coverUrl }` when the user corrects a wrong match. IGDB authenticates via Twitch client-credentials (`IGDB_CLIENT_ID` + `IGDB_CLIENT_SECRET`); both providers are optional — without keys, items fall back to a gradient tile

### Deployment

- **Dockerfile** — 3-stage build: client (Vite), server (tsc), production Alpine image with `espeak-ng` + `su-exec`
- **Caddy** — reverse proxy on :443 with self-signed TLS (required for browser microphone/camera APIs in kiosk)
- **Watchtower** — polls `ghcr.io` and auto-updates the running container
- **CI/CD** — `.github/workflows/docker-publish.yml` builds `linux/amd64` + `linux/arm64` on every push to `main`
- **Kiosk** — `scripts/kiosk.sh` launches TouchKio (Electron); `scripts/touchsphere-kiosk.service` is the systemd unit

## Key Constraints

- **Touch-only UI** — no hover states, all interactions must work with a finger tap
- **No stray zoom** — the same build runs on a phone, where two things zoom the viewport with nothing on screen to explain it. `touch-action: manipulation` is set on `*`, not on `body`: touch-action is not inherited, so on `body` alone a double-tap landing on a button (i.e. every control here) still zoomed. And iOS Safari zooms in whenever a field with a computed font-size under 16px takes focus, which these are by design — and because they also carry `inputMode='none'` no keyboard comes up with it, so the zoom arrives unexplained and stays. `maximum-scale=1` in the viewport meta is what suppresses that; iOS has ignored it for genuine pinch since iOS 10, so the a11y escape hatch survives there
- **ARM64 target** — Docker images must support `linux/arm64` for Raspberry Pi 5; test multi-arch builds before merging
- **Secure context required** — microphone and camera APIs require HTTPS; Caddy provides self-signed TLS even in local dev on Pi
- **Offline-capable voice** — wake-word detection (Vosk) and TTS fallback (espeak-ng) must work without internet
- **State persistence** — app mode, media list, and lock credential survive restarts via server-side JSON in the Docker volume
